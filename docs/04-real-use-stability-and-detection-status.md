# 실사용 안정성 및 감지 상태 마감

## 2026-07-29 LINE 연속 드롭 해제 좌표 고정

사용자가 LINE에 사진 4장씩 두 묶음을 연속 전송했을 때 두 묶음 모두 3장만
저장됐다. 로그에서 빠진 두 장은 Explorer 선택과 LINE 기준점까지는 관찰됐지만,
해제 대상 복구 유예 중 다음 드래그가 시작되며 모두
`next-drag-started-during-release-grace`로 취소됐다. 생성된 나머지 후보는 전송
확인과 저장까지 정상 완료돼 업로드 속도나 전송 확인 단계의 문제는 아니었다.

LINE 드롭 추적기는 마우스를 놓은 뒤 최대 48프레임 동안 일시적으로 가려진 대상을
다시 찾는다. 기존에는 이 기간 내내 현재 마우스 좌표를 사용했기 때문에 사용자가
다음 사진을 집으러 탐색기로 이동하면, 실제 LINE 위에 놓은 이전 사진도 LINE 밖에
놓인 것처럼 바뀌었다. 이제 마우스가 눌린 마지막 위치를 해제 좌표로 고정하고 복구
유예 전체에서 같은 좌표만 사용한다. 다른 앱에 놓은 드롭은 고정 좌표가 LINE 창
범위에 포함되지 않으므로 기존처럼 후보가 되지 않는다.

수정 전 회귀 테스트는 해제 좌표 기록기가 없어 컴파일 단계에서 실패했고 구현 뒤
LINE 수동 상태 테스트 7개가 통과했다. Release 전체 테스트는 Core 60개,
Diagnostics 15개, Platform Windows 421개, Infrastructure 184개, App 172개로
총 852개가 통과했다. x64 Developer 자체 설치 점검을 통과한 실행 파일은
254,183,821바이트, SHA-256
`F7ED60F6EB457C2BA08C8FF8C89B543D6A7CE3F7CFC414CA932EE76AA463D5A5`이며 제품
버전은 `1.5.0+developers`다. 메인 PC와 QA VM에 같은 해시로 배포했고 VM의
`Sentory*.backup-*` 파일은 0개임을 확인했다. 실제 4장 두 묶음 재검수는 남아 있다.

## 2026-07-29 LINE 감지 중 작업표시줄 경고음

Sentory 창을 작업표시줄에서 빠르게 최소화·복원할 때 다른 앱과 달리 Windows 시스템
경고음이 나고 가끔 창이 바로 올라오지 않는 현상을 메신저별 활성화 A/B로 분리했다.
설치본 1.3.33과 감지 전체 끔, Slack·WhatsApp 단독에서는 재현되지 않았고,
LINE 단독 활성화에서 반복적으로 재현됐다. Telegram 단독은 시작 직후 첫 클릭에서만
한 번 관찰돼 반복 현상의 주원인에서는 제외했다.

LINE은 연속 사진 전송 누락을 막기 위해 유휴 중에도 2초마다 최근 메시지 기준점을
갱신한다. 기존 코드는 16ms 드롭 감지 `DispatcherTimer` 안에서 LINE 주 창 열거와
접근성 문맥 검증을 시작한 뒤 나머지만 비동기로 넘겼다. 이 짧은 동기 구간이 WPF UI
스레드의 창 활성화 처리와 겹치면 Windows가 작업표시줄 입력을 즉시 처리하지 못했다.

기준점 캐시, 2초 갱신 간격, 드롭 시작 시 조기 기준점 수집은 유지한다. 유휴 갱신은
단일 실행 스케줄러가 백그라운드에서 LINE 창 탐색부터 접근성 수집까지 시작하며,
앞선 갱신이 끝나기 전에는 다음 갱신을 만들지 않는다. 느린 갱신이 호출 스레드를
막지 않고 순차 실행되는 회귀 테스트를 추가했다. 수정 개발자판은 LINE 단독과
Discord·카카오톡·Slack·WhatsApp·Telegram·LINE·WeChat 전체 활성화 상태에서
각각 반복 작업표시줄 클릭으로 재검수했고 경고음이 재현되지 않았다.
Release 전체 테스트는 Core 60개, Diagnostics 15개, Platform Windows 420개,
Infrastructure 184개, App 172개로 총 851개가 통과했다. x64 Developer 자체 설치
점검을 통과한 실행 파일은 254,183,309바이트, SHA-256
`31052651C734CFCDFE083D35E46CAFC8AA4016D600CABD939CF1F60DFF0DC97E`이며 제품
버전은 `1.5.0+developers`다.

## 2026-07-28 WeChat 전송 확인 감지

Windows용 WeChat 4.1.11.24의 실제 실행 환경에서 주 프로세스와 접근성 구조를
확인해 붙여넣거나 Explorer에서 드롭한 링크·사진을 전송 뒤에만 저장한다.

- 대화 접근성과 전송 확인은 주 창 프로세스 `Weixin.exe`와 이전 배포의
  `WeChat.exe`만 허용한다. `WeChatAppEx.exe`는 대화 문맥에서는 제외하되,
  업로드 중 주 창 위를 덮는 보조 표면일 때만 드롭 대상 유지에 사용한다.
- 네이티브 `Qt<버전>QWindowIcon` 주 창과 UIA의 `chat_input_field`,
  `chat_message_list`, `session_list`를 모두 확인해 채팅 입력 문맥만 후보로 만든다.
- Ctrl+V 시점에는 링크·사진 바이트를 메모리 후보로만 유지한다. 같은 대화에서
  Enter 또는 채팅 전송 버튼 입력이 발생하고 새 메시지 항목이 노출된 경우에만
  `Confirmed` 상태로 보관한다.
- 링크는 전송 입력 직전 작성창 또는 새 메시지에서 원래 URL이 확인돼야 한다.
  붙여넣은 링크를 지우고 다른 문장을 보내거나 다른 대화로 이동하면 후보를
  취소한다.
- 작성창 URL 판정은 UIA의 실제 `Value`·`Text` 값을 접근성 이름보다 우선한다.
  입력 안내 문구가 URL 대신 선택돼 정상 전송도 거부하던 문제를 이 기준으로
  수정했다.
- UIA에서 읽은 작성 내용과 메시지 본문은 일치 판정에만 사용하며 진단 로그나
  파일에 기록하지 않는다. 후보는 최대 8개, 대기 시간은 최대 2분으로 제한한다.
- Explorer에서 선택한 지원 이미지 파일이 실제 WeChat 주 창 위에 놓인 경우
  사진 바이트와 현재 대화의 메시지 목록을 후보로 유지한다. WeChat의 드롭
  미리보기 표면이 주 창을 가려도 포인터가 원래 채팅 창 범위 안에 있는 동안에는
  마지막으로 검증한 대상을 유지한다.
- 드롭 해제만으로는 저장하지 않는다. 같은 대화에서 Enter·전송 버튼 입력과 새
  사진 메시지 항목이 모두 확인된 뒤 `WeChatConfirmedDrop`으로 보관하며, 미리보기
  취소·사진이 아닌 파일·다른 창에 놓기·Esc 취소는 제외한다.
- Windows 드래그 피드백 표면이 포인터 아래 창 판정을 가로채는 간헐적 상황에
  대비해 마우스가 눌린 마지막 위치를 보존한다. 해제 때 엄격한 최상위 창 판정이
  실패해도 WeChat이 실제 전면 앱이고 그 위치가 검증된 주 창 범위 안일 때만
  대상으로 복구한다. 다른 앱이 전면이면 같은 화면 좌표여도 복구하지 않는다.

## 2026-07-29 느린 업로드와 연속 전송 후보 분리

실제 LINE·WhatsApp 재현 로그에서 첫 사진 후보가 전송 확정을 기다리는 동안
같은 사진을 다시 드롭하면 후속 후보가 `Duplicate`로 거부됐다. 이 중복 잠금은
Discord·LINE·Slack·Telegram·WeChat·WhatsApp의 사진 후보에 공통으로 적용돼,
네트워크가 느릴수록 정상적인 연속 전송을 오래 막는 구조였다.

- URL·사진 해시는 후보가 끝날 때까지 잠그지 않는다. 같은 대화에서 payload
  전체가 같은 등록이 0.5초 안에 반복된 경우만 한 드롭의 이중 통지로 간주한다.
- 같은 사진을 다시 보내거나 일부 사진이 겹치는 다음 묶음도 별도 후보로
  유지한다. 저장소 단계의 콘텐츠 병합과 전송 횟수 반영은 기존 정책을 따른다.
- 전송 입력 하나는 LINE·Slack·Telegram·WeChat·WhatsApp에서 가장 최근의
  미처리 후보 하나에만 연결한다. 느린 전송 중 쌓인 후보 전체가 한 번의 클릭에
  동시에 확정되는 것을 막는다.
- Discord는 한 번의 전송에 여러 붙여넣기 첨부가 합쳐질 수 있어 기존의 명시적
  URL·이미지 전송 배치 정책을 유지하되, 장기 해시 잠금만 짧은 이중 등록 판정으로
  교체한다.
- WeChat의 `WeChatAppEx.exe` 업로드 보조 표면은 포인터 아래 드롭 표면으로만
  인정한다. 이 프로세스를 주 대화나 전송 확인 문맥으로 승격하지 않는다.
- LINE은 드롭 시작 시점의 실시간 대화 기준점을 우선 사용한다. 최근 기준점이
  10초를 넘었고 사진 미리보기 전환 때문에 현재 메시지 목록이 비어 있을 때만,
  같은 LINE 프로세스와 같은 주 창에서 마지막으로 확인한 정상 기준점을 복구한다.
  다른 대화라면 이후 메시지 ID가 겹치지 않아 확정되지 않으며 LINE 재시작으로
  프로세스나 주 창이 바뀌면 복구 대상에서도 제외된다.
- LINE 드롭 해제 뒤 기준점 작업이나 이미지 읽기가 끝날 때까지 후보 등록을
  미루지 않는다. 등록 중인 주 창 문맥을 먼저 전송 감지에 노출해 그 사이 발생한
  사진 전송 창 클릭을 버퍼링하고, 이미지 후보가 준비되면 같은 드롭에 재생한다.
- LINE의 Qt 접근성 목록이 연속 전송 중 가상화되며 기존 메시지 런타임 ID를 모두
  교체할 수 있다. 일반 전송 버튼 입력만으로는 대화 겹침 조건을 완화하지 않고,
  대기 중인 사진 후보가 있으며 사진 전송 창 하단의 전송 영역을 누른 경우에만
  달라진 메시지 목록을 실제 결과로 인정한다. 확정 때 관찰한 목록은 즉시 다음
  드롭 기준점으로 이어 연속 전송마다 오래된 기준점을 재사용하지 않는다.
- LINE 사진 미리보기나 Windows 드래그 피드백 표면이 해제 순간 주 창 위에 남아도
  포인터가 마지막으로 검증한 LINE 창 범위 안이면 대상을 유지한다. 엄격한 포인터
  아래 창 판정이 실패할 때는 LINE이 실제 전면 앱인 경우에만 같은 좌표의 주 창을
  복구한다. 다른 앱이 전면이거나 포인터가 LINE 범위를 벗어난 경우는 제외한다.
- 다음 드래그가 이전 해제 유예보다 빨리 시작돼 이전 상태를 폐기하는 경우에는
  `next-drag-started-during-release-grace` 진단을 남겨 이후 실사용 경합을 구분한다.
- 후속 재검수에서 4장씩 두 묶음 모두 정확히 3장만 후보가 생성됐다. 생성된
  6개 후보는 전송 입력과 실제 메시지 변화까지 모두 확인됐지만, 빠진 두 드래그는
  묶음마다 LINE과 공유 원본을 본 메신저 조합이 달랐다. 각 메신저의 독립 16ms
  타이머 중 먼저 해제를 본 런타임이 공유 원본을 삭제해, 같은 해제 프레임을 늦게
  처리한 런타임이 합류하지 못한 경합으로 확인했다. 공유 세션은 해제 뒤 0.5초간
  최근 스냅샷을 보존하고 세대 번호로 런타임별 중복 소비를 막는다. 누름 구간을
  전부 놓쳤거나 누름만 보고 선택을 못 읽은 경우도 해제 프레임에서 한 번 복구한다.
  이 정책은 LINE·WeChat·Telegram·WhatsApp과 공통 수동 런타임을 쓰는 Discord·
  Slack·카카오톡에 함께 적용하며 Esc 취소는 스냅샷까지 즉시 폐기한다.
  Release 전체 테스트는 Core 60개, Diagnostics 15개, Platform Windows 404개,
  Infrastructure 184개, App 163개로 총 826개가 통과했다. x64 Developer 자체
  설치 점검을 통과한 실행 파일은 254,161,805바이트, SHA-256
  `5D7F2B52625395B0574BC7DC2AA0F3CFA123C982543A3E025718EE0A083D187A`이며

  - 공용 스냅샷의 0.5초를 선택 관찰 시점부터 계산해, 461ms 동안 이어진 드래그가
    끝난 뒤 LINE 타이머가 합류할 시간이 사실상 남지 않았다. 정상 해제 시각을

  - LINE 선택은 읽었지만 미리보기 표면 때문에 해제 대상이 나타나지 않아 다음

    하단 우측 50% 규칙에 4.1%p 모자라 거부됐다. 사진 후보가 있는 LINE 미리보기

## 적용 범위

Discord 감지 워커와 화면 상태 표시를 다음 기준으로 보강했다.

- Discord 채널 제목이나 창 핸들이 바뀌면 기존 대상 캐시를 폐기하고 다시 찾는다.
- Discord 재시작 뒤에는 이전 후보를 취소하고 새 창을 기준으로 감지 준비를 다시 수행한다.
- 감지 워커가 비정상 종료되면 한 번의 복구 작업만 시작하며, 복구가 끝나면 준비 완료 상태로 돌아간다.
- 링크와 사진 후보는 최대 8개까지만 동시에 처리하고, 같은 대화·같은 payload가
  0.5초 안에 이중 등록된 경우만 중복 후보로 만들지 않는다.
- 붙여넣기만 한 경우, Shift+Enter, 입력 삭제 및 전송 취소, Discord가 아닌 앱의 입력은 저장 확정으로 처리하지 않는다.
- 카카오톡의 기존 붙여넣기 감지 방식은 변경하지 않고 전체 회귀 테스트로 보호한다.
- 처음 연결하는 PC에서 Discord가 이미 실행 중이면 접근성 연결을 위한 재시작
  안내를 표시하고, 준비 완료 신호를 받기 전까지 안내 상태를 유지한다.
- 사진이 아닌 파일 드래그는 Sentory가 소유하지 않으며, 한 번 제외한 드래그는
  마우스 버튼을 놓을 때까지 감지 영역을 다시 표시하지 않는다.

- 라이트 모드와 다크 모드 보관함에서 `Discord 감지 · 감지 준비 완료` 문구와 의미 색상이 표시됐다.

- 실행 중인 Discord 감지 워커를 강제로 종료한 뒤 `worker-recovery-started`가 기록됐다.
- 약 3초 뒤 새 워커가 `target-cache-warmed`로 준비를 마치고 상태가 `감지 준비 완료`로 복귀했다.

실제 메시지 전송이 필요한 아래 항목은 Discord 비공개 작업장과
카카오톡 테스트 채팅에서 묶어서 확인한다. 자동 테스트 통과와 별개로,
배포 후보를 바꿀 때마다 한 번씩 확인한다.

1. [ ] Discord 채널 이동 뒤 URL과 사진을 연속 전송한다.
2. [ ] 붙여넣기만 한 뒤 취소하고, Shift+Enter 뒤 취소해 저장되지 않는지 확인한다.
3. [ ] Discord를 종료하고 다시 실행한 뒤 URL과 사진을 각각 전송한다.
4. [ ] Discord 이외의 앱에 같은 URL과 사진을 붙여넣어 저장되지 않는지 확인한다.
5. [ ] 카카오톡 채팅 입력창에서 URL과 사진을 붙여넣어 기존처럼 즉시 저장되는지 확인한다.
6. [ ] 카카오톡 검색창이나 다른 앱에서는 같은 동작이 저장되지 않는지 확인한다.
7. [ ] Sentory를 2시간 이상 실행한 뒤 감지 상태와 진단 로그에 반복 오류가 없는지 확인한다.
8. [ ] Sentory 실행 중 PDF, ZIP 등 일반 파일을 Discord와 카카오톡으로 드래그해
   깜빡임 없이 원래 파일 전송 화면이 유지되는지 확인한다.
9. [ ] 새 설정 폴더에서 Discord를 먼저 실행한 뒤 Sentory를 실행해 재시작 안내가

장시간 안정성은 100개 연속 워커 요청 테스트와 워커 강제 복구로 기본 경로를 검증했다. 실제 장시간 실행은 이후 일반 사용 중 진단 로그의 반복 오류, 워커 재시작 횟수, 누락 여부를 함께 관찰한다.

## 2026-07-21 초기 연결 상태 보완

새 설정 폴더와 공개판 1.1.32를 사용해 Discord가 먼저 실행된 환경을 다시
구성했다. 접근성 대상 목록을 읽지 못하는 동안 앱은 내부적으로 `Connecting`
상태였다. 현재 설정 화면은 작은 스위치를 표시하면서 이름 아래에 구체적인 감지
상태도 함께 안내한다. 재연결이 필요한 경우에는 Discord 행에 재연결 버튼을
노출한다.

- 연결 준비 중과 복구 중 상태를 보관함, 설정과 트레이에 같은 문구로 표시한다.
- 초기 준비를 15회 시도한 뒤에도 접근성 대상 목록을 읽지 못하면 재연결 필요
  상태로 전환한다.
- 채널 이동 중 잠깐 발생하는 단일 실패는 기존처럼 복구 대상으로 처리해
  불필요한 Discord 재시작을 요구하지 않는다.
- 설정창이 열린 동안 상태가 바뀌어도 창을 다시 열지 않고 현재 문구를 갱신한다.

회귀 테스트는 짧은 실패와 긴 초기 실패를 따로 다루며, 준비 중·복구 중·재연결
필요 상태가 보관함과 트레이에 같은 기준으로 표시되는지 확인한다.

## 2026-07-21 재연결 완료 알림 동기화

Discord 재연결 뒤 설정 화면이 `감지 준비 완료`로 바뀌어도 보관함 상단의 이전
연결 복구 알림이 남을 수 있었다. 감지 상태와 재연결 플래그는 정상적으로
복구됐지만, 상단 알림에 쓰는 최근 런타임 오류가 별도 값으로 남아 있었기
때문이다.

- `discord-detection-unavailable` 오류 뒤 `Ready` 상태를 받으면 연결 복구
  알림을 자동으로 닫는다.
- 연결 준비 중과 복구 중에는 사용자가 현재 상황을 알 수 있도록 알림을
  유지한다.
- 자동 정리 실패 등 Discord와 무관한 최근 오류는 Discord 준비 완료 상태로
  지우지 않는다.
- 재연결 필요 여부와 최근 오류 표시가 같은 `Ready` 상태에서 함께 정리되는지
  자동 테스트로 확인한다.

## 2026-07-21 Discord 자체 재실행 뒤 자동 재탐색

Sentory가 감지 준비를 마친 뒤 Discord만 업데이트되거나 자체 재실행되면
Discord 프로세스와 접근성 대상이 바뀔 수 있다. 이때 전송 확인 결과는
`message-list-unavailable`이었지만 런타임은 상태를 `Connecting`으로 바꾸기만
하고 준비 작업을 다시 시작하지 않아 연결 준비 중에 계속 머물렀다.

- 전송 확인 중 메시지 목록이나 현재 창 검증을 잃으면 새 Discord 창을 대상으로
  접근성 준비 작업을 자동으로 다시 실행한다.
- 재탐색이 성공하면 `Ready`로 복귀하고 Discord를 종료하거나 재시작하지 않는다.
- 앱을 켰지만 Discord 채팅방을 아직 열지 않아 메시지 목록이 없는 경우에는
  `Connecting`을 유지하며 재연결 오류를 표시하지 않는다.
- 실제 링크나 사진 전송 뒤 새 창에서도 접근성 대상을 계속 읽지 못할 때만
  `ReconnectRequired`로 전환해 설정에 Discord 재시작 버튼을 표시한다.
- 작업자 프로세스 장애는 기존처럼 `Recovering` 상태에서 작업자 준비를 다시
  수행하고, 렌더러 접근성 루트가 명확히 없으면 즉시 재연결 필요로 분류한다.
- 회귀 테스트에서 초기 메시지 목록 부재는 조용히 대기하고, 전송 뒤 목록 유실,
  작업자 장애와 접근성 루트 부재가 각각 자동 재탐색·작업자 복구·사용자
  재연결로 이어지는지 확인한다.

## 2026-07-21 Windows 로그인 시 Discord 연결 유지

Discord 접근성 옵션은 실행 중인 프로세스에 나중에 붙일 수 없고, Discord를
시작할 때 전달해야 한다. 이전에는 Sentory와 Discord가 Windows 로그인과 함께
각자 시작하면 실행 순서에 따라 Discord가 옵션 없이 먼저 열릴 수 있어 같은
PC에서도 재부팅할 때마다 재연결 안내가 나타날 가능성이 있었다.

- Sentory의 Windows 자동 실행과 Discord 감지를 모두 켠 동안 Windows의
  Discord 시작 명령을 Sentory가 관리한다.
- 기존 Discord 시작 명령과 레지스트리 값 형식을 별도 키에 먼저 백업한 뒤
  `--force-renderer-accessibility`가 포함된 명령을 등록한다.
- Sentory와 Discord 중 어느 쪽이 먼저 실행돼도 Windows가 Discord를 접근성
  옵션과 함께 시작하므로 일반적인 재부팅에는 재연결이 필요하지 않다.
- Sentory 자동 실행 또는 Discord 감지를 끄면 기존 Discord 시작 명령을
  복원한다. 관리 중 사용자가 값을 바꾸거나 삭제했다면 그 선택을 덮어쓰지 않는다.
- 설치형 제거 프로그램은 파일을 지우기 전에 같은 복원 명령을 실행한다.
- Discord 업데이트가 시작 명령을 다시 쓰는 상황에 대비해 앱 시작과 6시간
  유지보수 주기마다 관리 명령을 확인하고 다시 적용한다.
- Discord가 업데이트 중 자체 재실행한 현재 프로세스에는 옵션을 사후 적용할 수
  없으므로, 자동 재탐색 실패 시에만 기존 재연결 안내를 유지한다.

## 2026-07-22 Discord 사진 첨부 취소와 다음 전송 분리

Discord 사진 후보는 전송 확인 전까지 최대 2분간 유지된다. 이전에는 첨부
미리보기의 제거 버튼을 누른 사실을 Sentory가 알지 못해, 취소한 사진과 다음에
붙여넣어 실제 전송한 사진을 같은 묶음으로 저장할 수 있었다.

- 사진 후보가 기다리는 동안 Discord 입력 영역의 `첨부 파일 제거` 버튼 수를
  접근성 작업자에서 짧은 간격으로 확인한다.
- 화면에서 확인한 첨부 수보다 미전송 후보가 많으면 오래된 단일 사진 후보부터
  폐기한다. 따라서 취소한 첫 사진은 다음 Enter 전송에 합쳐지지 않는다.
- 방금 붙인 사진 미리보기가 만들어지는 동안에는 500ms 보호 시간을 적용해
  정상 후보를 취소로 오판하지 않는다.
- 접근성 버튼을 한 번도 확인하지 못한 환경에서는 후보를 임의로 지우지 않는다.
  여러 사진을 실제로 남겨 둔 경우에도 확인된 첨부 수와 후보 수가 같아 기존
  묶음 저장 동작을 유지한다.
- 한 번에 붙인 여러 사진 중 일부만 제거해 어느 사진인지 구분할 수 없는 경우에는
  전체 후보를 지우지 않는다. 잘못된 사진을 한 장 취소하고 새 사진 한 장을
  붙여넣는 이번 재현 경로를 우선 정확하게 처리한다.

첫 구현은 첨부 수를 세기 전에 메시지 목록을 찾고 Discord 전체 접근성 트리를
순회해, 실제 PC에서 조회가 15초 안에도 끝나지 않았다. 그 사이 Enter가 먼저
처리되어 취소 후보가 그대로 묶이는 재현 로그를 확인했다.

- Discord가 서버 채널을 화면에 띄우고도 렌더러 HWND의 접근성 루트에는 이전
  DM을 남기는 경우가 있다. 렌더러 루트의 `count=0`을 현재 초안으로 오인하지
  않도록 사진 초안 확인은 메인 Discord 창의 현재 문서를 직접 읽는다.
- 초안 확인은 일시적으로 사라질 수 있는 렌더러 자식 HWND에 의존하지 않고 메인
  창과 Discord 프로세스만 검증한다. 링크와 실제 전송 확인은 기존처럼 렌더러까지
  엄격하게 검증한다.
- 상단 메뉴, 왼쪽 서버·친구 탐색 영역과 오른쪽 멤버 목록은 순회하지 않고 화면
  하단 채팅 초안 영역과 겹치는 접근성 가지만 확인한다. 입력창 쪽부터 역순으로
  탐색하고, 현재 후보 수만큼 제거 버튼을 찾으면 즉시 종료한다.
- 사진 초안이 실제로 열린 상태에서 최신 코드에 같은 요청을 5회 실행해 모두
  `count=1`을 확인했다. 전체 소요 시간은 3.75초였고 후속 응답 간격은
  600~802ms였다. 확인 요청은 앞선 요청이 끝난 뒤 100ms 간격으로 이어지며,
  취소 후 다음 사진을 복사하는 동안 0개 상태를 확인해 오래된 후보를 전송 전에
  제거한다.

## 2026-07-22 Discord에서 삭제한 URL 후보 제외

Enter 시점에 같은 입력창의 미전송 URL 후보를 모두 묶은 뒤, 전송 메시지에도
모든 후보가 있어야 한다고 검사하고 있었다. 먼저 붙인 URL을 삭제하고 새 URL만
전송하면 삭제된 URL 때문에 묶음 전체가 취소돼 새 URL도 저장되지 않았다.

- 접근성 작업자는 실제 전송 메시지에서 발견한 후보 URL 목록을 확인 응답에
  포함한다.
- 런타임은 해당 목록과 대기 후보의 교집합만 최종 저장한다. 먼저 붙인 URL을
  지웠다면 새 URL만 저장하고, 여러 URL을 실제로 함께 보냈다면 모두 저장한다.
- 작업자 응답 직렬화, 부분 URL 확인 조건과 최종 저장 선택을 회귀 테스트로
  고정한다.
- 수정 검수판에서 후보 2개 중 첫 URL을 삭제하고 새 URL만 전송했다. 로그는
  `urls=1`, `Confirmed`, `eventApplied=True`를 기록했고, DB에도 새 URL 캡처
  이벤트 1건만 생성됐다. 기존 항목의 저장·전송 횟수와 마지막 저장 시각이
  갱신돼 최신순 첫 항목으로 이동하는 것도 확인했다.

## 2026-07-23 전체 감지 일시정지와 설정창 동기화

트레이의 `감지 일시정지`는 런타임 전체를 잠시 멈추는 상태이고, 설정창의
스위치는 각 메신저를 사용할지 저장하는 설정이다. 설정창은 각 스위치 상태와
이름 아래의 현재 감지 상태를 함께 보여준다.

- 전체 일시정지 상태를 `App`에서 `GalleryWindow`를 거쳐 열린 설정창까지
  전달한다. 일시정지한 뒤 설정창을 새로 열 때도 현재 상태를 함께 넘긴다.
- 개별 설정이 켜진 메신저의 스위치는 전체 일시정지 중에도 켜진 채 유지되고,
  이름 아래 상태만 `감지 일시정지됨`으로 바뀐다. 툴팁과 UI Automation 이름도
  같은 상태를 반영하며 임시 정지가 영구 설정을 바꾸거나 저장하지 않는다.
- 개별 설정이 꺼진 메신저는 전체 일시정지 여부와 관계없이 스위치가 꺼진 채
  유지되고, 이름 아래에는 해당 메신저 감지를 사용하지 않는다고 표시한다.
- 전체 일시정지 중에는 Discord 재연결 버튼을 숨긴다. 다시 시작한 뒤 실제 연결
  상태가 재연결을 요구할 때만 버튼을 복원한다.
- 상태 우선순위와 한국어·영어·일본어·중국어 일시정지 문구를 회귀 테스트로
  확인한다.

## 2026-07-24 Discord 프로세스별 자동 연결 복구

1.4.2는 초기 준비 작업이 15회 실패하면 `Connecting` 상태만 남기고 작업을
끝냈다. Discord를 먼저 실행한 뒤 Sentory를 켜거나, 두 프로그램 중 하나를 다시
실행한 환경에서는 채팅 화면이 나중에 준비돼도 상태를 다시 확인할 계기가 없었다.

- Sentory는 Discord 메인 창의 PID를 감지 준비 전에는 3초, 준비 완료 뒤에는
  10초 간격으로 확인한다. 준비 완료 뒤에는 현재 프로세스의 종료 이벤트도 함께
  기다리므로 Discord가 먼저 꺼지면 10초 타이머를 기다리지 않고 즉시 깨어난다.
- 새 메인 PID가 나타나면 `Win32_Process.CommandLine`을 한 번만 읽는다.
  `--force-renderer-accessibility`가 빠졌으면 기존 15회 확인과 30초 대기를
  생략하고 바로 `ReconnectRequired`로 전환한다.
- PID 변경 신호가 접근성 확인 사이의 2초 대기에서 들어오면 해당 대기를 새
  프로세스 신호로 처리하고 15회 초기 확인을 처음부터 다시 시작한다. 신호를
  소비한 뒤 낡은 주기를 끝내고 30초 저빈도 대기로 내려가던 지연을 막는다.
- 실행 옵션이 이미 있거나 명령을 읽지 못한 경우에는 자동 재시작하지 않고
  기존 연결 준비를 수행한다. 명령 확인은 PID가 바뀔 때만 실행하므로 상시 WMI
  조회는 없다.
- 최초 15회 준비 뒤에도 채팅 화면이 없으면 작업을 종료하지 않는다. 이후에는
  접근성 확인을 30초에 한 번으로 낮춰 Discord가 로그인되거나 채팅방이 열릴
  때까지 기다린다.
- 준비 완료 뒤에는 접근성 작업이 종료되므로 상시 반복되는 트리 순회가 없다.
  10초 확인은 Discord 프로세스와 메인 창 핸들만 읽는다.
- 렌더러 접근성 루트 부재가 한 번 확인된 뒤 창 교체로 요청을 만들지 못해도
  같은 준비 묶음에서는 더 강한 실패 상태를 유지한다.
- 메시지 목록을 찾지 못했다는 이유만으로는 재시작 대상으로 올리지 않는다.
  로그인 중이거나 채팅방을 열지 않은 정상 상태와 구분할 수 없고, 실행 옵션이
  이미 있는 Discord를 다시 켜도 해결되지 않기 때문이다.
- 다만 같은 접근성 작업자가 초기 15회 대상 재탐색을 모두 실패하면 Discord를
  재시작시키기 전에 Sentory 내부 작업자만 한 번 교체한다. 실제 2026-07-29
  재현에서는 기존 작업자가 `message-list-unavailable`로 30초 간격 무한 대기한
  반면 같은 Discord 창에 새 작업자를 연결하자 즉시 `target-cache-warmed`가
  확인됐다. 새 작업자도 실패할 때만 기존 로그인·채팅방 대기 또는 명시적
  재연결 정책으로 돌아간다.
- 자동 재시작 안내는 15초 카운트다운과 `취소`, `지금 재시작` 버튼을 함께
  제공한다. 같은 PID에는 한 번만 표시하고, 카운트다운 중 PID가 달라지면
  이전 프로세스를 대상으로 한 재시작을 건너뛴다.
- `지금 재시작`을 누르거나 카운트다운이 끝나면 메인 화면의 큰 재시작 배너를
  즉시 숨기고 `연결 준비 중`으로 전환한다. Discord 종료와 새 프로세스 확인을
  기다리는 동안 이미 선택한 재시작 버튼을 계속 보여 주지 않는다. 실행에
  실패한 경우에만 재시작 배너를 복원한다.
- 사용자가 취소하면 현재 프로세스를 자동으로 다시 끄지 않는다. 설정의 수동
  재연결은 유지하며, 새 Discord PID가 나타나면 자동 연결 판단을 새로 시작한다.
- 자동 안내를 취소한 뒤 큰 배너에서 `나중에`를 눌러도 재연결 필요 상태 자체는
  해제하지 않는다. 큰 배너 대신 헤더 아래의 작은 `Discord 재연결 필요` 상태를
  표시하고, 연결 준비를 시작하거나 준비 완료가 확인되면 이 표시를 갱신한다.
- Discord가 종료된 뒤에는 새 실행을 기다릴 뿐 Sentory가 임의로 Discord를
  다시 켜지 않는다. Sentory가 직접 Discord를 시작하는 기존 경로는 처음부터
  접근성 옵션을 전달한다.
- 재시작 버튼을 누른 뒤 상태를 임의로 `Ready`로 바꾸지는 않는다. 실제 기록상
  Discord가 새 메인 창을 만드는 데 약 6초, 메시지 목록과 접근성 캐시가
  준비되는 데 추가 2~7초가 걸렸다. 이 구간은 `Connecting`으로 두되 새 PID에서
  불필요한 30초 대기가 추가되지 않도록 한다.

## 2026-07-27 보관함 사진 재복사 원본 유지

파일로 처음 저장된 PNG를 보관함에서 복사하면 WPF 비트맵으로 바뀌면서 XMP,
DPI와 색상 형식이 달라질 수 있다. 기존 중복 키는 저장 파일 전체의 SHA-256이라
보이는 픽셀이 같아도 다시 붙여넣은 사진이 새 카드로 만들어졌다.

- 단일 사진 복사는 메신저 호환용 표준 비트맵과 원본 이미지 바이트를 담은
  `Sentory.ImageContent.v1` 형식을 함께 기록한다.
- Discord나 카카오톡은 기존 표준 비트맵을 사용하고, Sentory는 전용 형식이
  유효하면 원본 파일 바이트와 파일명을 우선 사용한다.
- 전용 형식은 64MiB 이미지 상한, 헤더 길이, UTF-8 메타데이터와 실제 이미지
  디코딩을 검증한다. 형식이 없거나 손상됐으면 기존 파일 드롭 또는 비트맵 PNG
  변환 경로를 유지한다.
- 카드와 상세창의 단일 사진 복사가 같은 구성 요소를 사용한다. 복사할 때 내부
  `images/<SHA-256>.<확장자>` 파일명이 아니라 항목이나 묶음 구성원에 저장된
  원본 파일명을 함께 전달한다.
- 이전 개발자판이 전용 데이터에 넣은 `SHA-256.확장자` 이름은 같은 사진의
  의미 있는 기존 원본명을 덮어쓰지 못한다. 원본 바이트·파일명 왕복 보존,
  내부 해시 이름 방어와 손상 데이터 거부를 자동 테스트로 고정한다.

  `line-capture-applied`로 저장됐다. 후보 제한 2분 안의 느린 업로드는 누락
  원인이 아니며, 같은 파일의 중복 후보는 활성 해시로 한 번만 저장한다.
- 연속 LINE 드롭은 일부 해제 시 사진 창 전환 동안 대상을 약 256ms 안에 다시
  찾지 못해 취소됐다. 해제 대상 유예를 약 768ms로 늘리고, 사진을 놓기 전에
  마지막 정상 대화 기준점을 비동기로 보존해 전환 첫 프레임의 빈 메시지 목록에
  의존하지 않도록 했다. LINE 26.3처럼 사진 창이 별도 `AlertWindow`가 아니라
  메인 Qt 창에 통합된 경우에도, 활성 사진 후보가 있는 같은 프로세스의 창 하단
  오른쪽 클릭을 전송 입력 증거로 연결한다. 클릭만으로 저장하지 않고 기존
  메시지 겹침과 새 메시지 ID를 함께 확인하므로 취소 클릭은 저장되지 않는다.
- 최종 개발자판 실제 검수에서 LINE 사진 전송 세 번이 모두 드롭 전 기준점,
  통합 Qt 창 전송 클릭, 새 메시지와 `capture-applied`까지 이어졌고 사용자가
  보관함 인식을 확인했다. Release 전체 테스트 799개와 x64 개발자판 게시 자체
  점검을 통과했다.
- 이후 즉시 드롭 재검수에서 실패한 세 건은 LINE 창 진입부터 해제까지
  0.21~0.30초뿐이어서, 드래그 중 시작한 UIA 기준점 수집이 사진 창 전환 뒤
  `messages=0`으로 끝났다. 반면 0.6초 이상 머문 이전 성공 건은 드롭 전에
  기준점이 준비됐다. LINE의 보이는 정상 대화 기준점을 2초 간격으로 조용히
  갱신해 최대 10초만 보존하고, Explorer에서 이미지 드래그가 시작되는 순간에도
  커서 도착 전 메인 창을 찾아 조기 갱신한다. 캐시는 같은 프로세스·창에서만
  사용하며 이후 기존 메시지 ID 겹침, 명시적 전송 입력과 새 메시지 ID 확인은
  그대로 유지한다.
