# 1.0.0 성능 점검

## 2026-07-29 Tauri 2.0 개발자판 최종 기준

실제 사용자 보관함 117개에서 Release 개발자판을 새로 시작해 Tauri 호스트,
WebView2 자식과 상시 C# 엔진을 함께 측정했다. 첫 갤러리 요청부터 첫 페이지
80개가 도착하기까지 923ms였고, 첫 보이는 이미지가 그 뒤 48ms에 표시됐다.
같은 엔진을 재사용한 실제 필터 전환은 KakaoTalk 36ms, WhatsApp 22ms,
LINE 10ms였으며 각 응답의 `count`와 `total`은 각각 8/8, 7/7, 24/24로
일치했다. 전체 117개 복원과 두 번째 37개 페이지도 10~81ms 범위였다.

별도 임시 SQLite 보관함에는 URL 2,000개를 넣고 500개와 2,000개 지점에서
최신순 80개 페이지, 검색, Discord 필터와 오래된순을 실제 저장소 계약으로
조회했다. 최초 500개 최신순 쿼리는 연결·실행 준비를 포함해 82.1ms였고,
나머지 500개 쿼리는 1.0~2.9ms였다. 2,000개에서는 최신순 1.5ms, 검색
6.5ms, 메신저 필터 1.2ms, 오래된순 1.1ms였다. 테스트는 절대 시간으로
실패시키지 않고 결과 개수와 80개 페이지 상한을 회귀 조건으로 고정하며,
로컬 측정 시간은 상세 테스트 출력으로 남긴다.

유휴 화면에서 전체 프로세스 트리는 12개였고 작업 집합 672.6MB, 전용 메모리
372.7MB였다. 구성은 Tauri 호스트 57.6/11.0MB, WebView2 프로세스 합계
426.7/288.9MB, 두 C# 엔진 162.5/69.0MB, 콘솔 호스트 합계
25.8/3.8MB다. 같은 순간 오래 실행 중인 WPF 두 프로세스는 작업 집합
673.7MB, 전용 메모리 751.1MB였지만 실행 시간이 달라 직접 우열 수치로 쓰지
않고 현장 참고값으로만 기록한다. Tauri의 카드 DOM은 1322px 창에서 화면과
위아래 세 행을 합친 최대 36개로 제한되고, 데이터 DTO도 페이지당 80개와 인접
페이지에 한정된다.

필터·정렬·탭 전환은 이전 전체 개수만큼 빈 카드를 다시 만들지 않고, 새 SQL
페이지 응답이 도착하면 항목 배열과 가상 높이를 한 번에 교체한다. 선택 모드도
기존 카드 DOM과 디코딩된 이미지를 유지한 채 체크 표시와 테두리만 바꾼다.
스크롤 버퍼는 화면 앞뒤 세 행으로 넓혔고, 범위가 한 행씩 이동할 때 겹치는 카드
DOM과 이미지 요소를 그대로 옮겨 쓴다. 따라서 스크롤마다 전체 가시 카드를
재생성하지 않고 새 가장자리와 로딩 완료된 스켈레톤만 교체한다.
테마 변경과 그 설정 저장 응답도 `renderRevision`을 올리지 않는다. CSS 테마 토큰과
Windows 제목 표시줄 색만 바꾸고 번역이 필요한 보이는 텍스트는 기존 카드 요소에
제자리 반영하므로, 이미 디코딩한 썸네일을 다시 만들거나 반짝이게 하지 않는다.
Release 전체 자동 테스트는 Core 60개, Diagnostics 15개, Platform Windows
425개, Infrastructure 187개, Engine Bridge 11개, App 184개로 총 882개가
통과했다. 묶음 9장 페이로드·앱 정보 링크 허용 목록·라이선스 포함 내용을
검증하는 Rust 단위 테스트 3개, Tauri Release 빌드와 JavaScript 문법 검사도
통과했다.

## 2026-07-29 Tauri UI 전환 기준

제품 UI를 Tauri 2로 옮기되 메신저 감지와 데이터 처리는 C# 엔진으로 유지한다.
첫 구조 검증판은 최근 500개 DTO를 한 번에 받고, 카드 DOM은 화면과 위아래 두
행으로 제한한다. 따라서 현재 결과는 IPC와 가상 스크롤의 연결 확인이며 대용량
성능의 최종 결과가 아니다. 다음 단계에서 검색·필터·정렬이 포함된 SQL 페이지
조회와 취소 가능한 이미지 요청으로 바꾼다.

메모리는 작업 관리자의 `Sentory` 한 행만 보지 않고 Tauri 호스트, WebView2 자식
프로세스와 C# 엔진의 전용 메모리를 모두 합산한다. 118개·500개·2,000개에서 시작,
첫 카드, 탭·필터·정렬, 빠른 왕복 스크롤과 10분 뒤 회수량을 같은 조건으로 비교한다.
구체적인 전환 기준은 [Tauri UI 전환 로드맵](./11-tauri-ui-migration-roadmap.md)에
기록한다.

WPF 기준판은 별도 WebView2 갤러리 시제품을 포함하지 않는 1.5.0으로 고정한다.
Tauri 비교에서 WPF 측은 항상 이 실행 경로를 사용한다. 과거 WebView2 카드 시제품의
수치는 서로 다른 UI 구조의 참고값일 뿐, 현재 기준판이나 Tauri 결과로 간주하지
않는다.

디코딩, 컬렉션 갱신 병합, 첫 동기화 8초 유예와 UI 입력 중 동기화 취소를 적용한

WebView2는 1.5.0에 포함되지 않았으며 별도 시제품에서 프로세스 전체 메모리와
반응 시간을 다시 측정한 뒤 전환 여부를 정한다.

## 2026-07-29 갤러리 필터·정렬 증분 갱신

전체·사진·링크·즐겨찾기 탭이나 메신저 필터·정렬을 바꿀 때 쿼리 자체는 실제
116개 보관함에서 충분히 빨랐지만, 결과를 `ObservableCollection`의 전체
`Reset`으로 적용했다. 사용자에게 계속 보일 카드도 WPF 가상화 패널에서 모두
제거되어 카드 템플릿과 썸네일 바인딩을 다시 만드는 것이 짧은 버벅임의 원인이었다.

새 경로는 기존 카드 뷰모델을 항목 ID로 다시 사용하면서 결과에서 빠진 항목만
제거하고, 새 항목만 삽입하고, 정렬이 바뀐 기존 항목은 이동한다. 가상화 패널도
Remove·Replace·Move 알림의 실제 컨테이너 범위만 반영하므로 필터 결과에 남은
화면 카드는 같은 컨테이너를 유지한다. 선택 직후 탭 강조와 결과가 함께 바뀌는
기존 동작에는 지연이나 로딩 단계를 추가하지 않았다.

같은 개발 PC와 보관함에서 실제 UI 자동화 클릭 반환 시간을 비교했다. 수정 전
전체에서 사진 탭으로 전환은 385.3ms였고, 수정 후 전체·사진·링크·즐겨찾기 탭은
57.9~66.3ms였다. 오래된순·최신순 반복 전환은 61.1~68.9ms, LINE 메신저 필터
적용은 61.1ms, 전체 메신저 복원은 78.2ms였다. 사진·링크·즐겨찾기·LINE 결과의
종류와 최종 `전체 / 최신순 / 전체 메신저` 상태도 화면에서 확인했다.

컬렉션이 Reset 없이 필터 제외 항목만 제거하는지, 정렬 시 기존 항목을 이동하는지,
실제 WPF `ItemsControl`에서 필터 뒤 남은 카드가 동일한 컨테이너를 쓰는지를 자동
테스트로 고정했다.

## 2026-07-29 LINE 유휴 기준점 갱신의 UI 스레드 분리

LINE 연속 드롭의 첫 후보 누락을 막는 최근 메시지 기준점은 유휴 중 2초마다
갱신한다. 기존에는 LINE 주 창 열거와 접근성 문맥 검증이 WPF UI 스레드에서
시작돼, 작업표시줄 최소화·복원 입력과 겹칠 때 Windows 경고음과 창 반응 지연을
만들 수 있었다.

16ms 드롭 포인터 폴링과 2초 기준점 갱신 주기는 바꾸지 않았다. 기준점 갱신만
중복 실행을 막는 백그라운드 스케줄러로 옮겨 LINE 창 탐색부터 접근성 수집까지
UI 스레드 밖에서 수행한다. 따라서 빠른 Explorer 드롭 감지와 기준점 캐시 효과는
유지하면서 창 활성화 입력과의 경합을 제거한다. 느린 갱신을 의도적으로 막아도
호출 측이 즉시 반환하고, 진행 중·간격 이전의 중복 갱신을 만들지 않는 테스트로
고정했다.
Release 전체 테스트 851개와 x64 Developer 자체 설치 점검을 통과했고, LINE 단독과
전체 메신저 활성화 상태의 반복 작업표시줄 전환에서도 경고음이 재현되지 않았다.

## 측정 결과

현재 개발 PC와 실제 사용자 데이터로 측정했다. 이 값은 절대 성능 기준이 아니라
같은 환경에서 회귀 여부를 확인하기 위한 참고값이다.

| 항목 | 결과 |
|---|---:|
| 창 표시 준비 시간 | 3회 평균 706ms, 688~742ms |
| 10초 유휴 CPU | 0.00% |
| 본 앱 작업 집합 | 평균 184.1MB |
| 본 앱 전용 메모리 | 평균 181.7MB |
| 기존 로그의 보관함 갱신 | 일반 항목 약 2~110ms |
| 기존 로그의 사진 3장 묶음 갱신 | 약 230~250ms |

WPF와 자체 포함 .NET 런타임을 함께 올리는 데 필요한 기본 메모리가 대부분을
차지했다. 유휴 상태에서 반복적으로 CPU를 쓰는 현상은 확인되지 않았다.
Discord와 카카오톡 드래그 감지는 짧은 주기로 실행되지만, 실제 측정에서는
CPU 사용량이 0.00%로 유지됐다. 감지 속도에 직접 영향을 주는 부분이라 이번에는
주기를 바꾸지 않았다.

SQLite 조회는 최근 500개 항목을 한 번에 가져온 뒤 컬렉션 구성원을 묶어서 읽는다.
항목마다 별도의 쿼리를 반복하는 구조는 아니며, 정렬·즐겨찾기·복사 기록에 필요한
인덱스도 적용돼 있다.

## 발견한 병목과 수정

새 항목이 저장되거나 링크 미리보기가 완성될 때 보관함은 최신 데이터를 다시
읽는다. 기존 구현은 이때 내용이 바뀌지 않은 썸네일까지 매번 파일에서 읽고
디코딩했다. 항목이 적을 때는 눈에 띄지 않지만 사진과 묶음이 늘수록 UI 스레드의
작업량과 임시 메모리가 함께 늘어날 수 있다.

파일 크기와 마지막 수정 시각이 같은 썸네일은 이전에 만든 이미지를 다시 쓰도록
파일 기반 LRU 캐시를 추가했다. 캐시는 약한 참조를 사용하므로 화면에서 더 이상
쓰지 않는 이미지를 강제로 메모리에 남겨 두지 않는다. 파일이 바뀌거나 삭제되면
기존 값을 사용하지 않고 다시 읽는다.

다음 동작을 자동 테스트로 고정했다.

- 바뀌지 않은 파일은 한 번만 읽음
- 파일 내용이 바뀌면 다시 읽음
- 캐시 한도를 넘으면 가장 오래 쓰지 않은 항목부터 제거
- 파일이 삭제되면 남아 있던 캐시 항목도 제거

## 배포 전 판정

시작 시간과 유휴 자원 사용량에서 배포를 막을 만한 문제는 확인되지 않았다.
Release 빌드 경고와 오류는 없었고 자동 테스트 206개, x64 설치·실행·제거
왕복 검증을 모두 통과했다. 이 결과를 기준으로 1.0.0 배포 대상으로 판정한다.

실제 Windows on ARM 장치 검수, 수백 개 이상의 고해상도 묶음을 연속으로 추가하는
장시간 부하 시험, 코드 서명은 후속 점검으로 남긴다.

## 2026-07-22 외부 이미지 자원 상한

클립보드 파일과 Discord 첨부 응답을 메모리로 읽을 때 기존 구현은 파일 크기에
관계없이 먼저 복사했고, Discord 응답은 `MemoryStream.ToArray` 과정에서 같은
바이트를 한 번 더 할당할 수 있었다. 다음 상한과 할당 정책을 공통 적용했다.

- 사진 한 장의 인코딩 바이트 최대 64MB
- 한 전송 묶음 최대 12장, 인코딩 바이트 합계 최대 256MB
- 가로·세로 최대 32,768픽셀, 총 최대 6천만 픽셀
- 크기를 아는 파일과 HTTP 응답은 정확한 배열을 한 번만 할당
- 크기를 모르는 응답은 64MB를 넘는 즉시 중단

이 제한은 일반 스크린샷과 8K 이미지까지 허용하면서 비정상적으로 큰 파일이나
압축 이미지가 장시간 메모리를 점유하는 상황을 차단한다. 제한된 사진을 저장하지
못해도 Discord·카카오톡의 원래 전송은 가로채지 않는다.

## 2026-07-21 언어 변경과 카드 가상화

언어를 바꿀 때 기존 갤러리는 최근 항목 최대 500개의 카드 뷰모델과 화면 요소를
한 번에 다시 만들었다. 썸네일 캐시가 있어도 `ItemsControl`의 전체 Reset과 전역
언어 리소스 변경이 모든 카드에 전달돼 UI 스레드가 잠깐 멈췄다.

언어 변경은 다음 순서로 나눠 처리한다.

1. 앱 공용 번역 리소스 묶음 교체와 설정창·갤러리 상단 문구 갱신
2. 현재 화면에 배치된 카드의 언어 의존 문구 갱신
3. 렌더 프레임 반환
4. 화면 밖 카드 문구를 24개씩 나눠 백그라운드 우선순위로 갱신
5. 설정 파일 저장

갤러리 패널은 고정 카드 크기를 기준으로 현재 화면과 위아래 두 줄만 생성한다.
스크롤로 화면을 벗어난 컨테이너는 제거하지 않고 다음 카드에 재사용하며,
썸네일은 기존 파일 기반 LRU 캐시를 그대로 사용한다. 창 너비가 바뀌면 한 줄의
카드 수와 전체 높이를 다시 계산하고 마지막 줄은 기존처럼 가운데 정렬한다.

가상화 회귀 테스트는 500개 항목에서 화면과 버퍼에 필요한 카드만 생성되는지,
중간 위치로 이동하면 첫 화면 컨테이너가 새 항목에 재사용되는지, 마지막 일부
행이 가운데 정렬되는지를 확인한다. 언어 변경 계획 테스트는 현재 보이는 카드가
첫 묶음에 들어가고 나머지가 지정된 크기를 넘지 않는 묶음으로 나뉘는지 확인한다.

## 2026-07-29 언어 리소스 갱신 통합

기존 분할 갱신 이후에도 언어 선택 시 번역 키 340개를 설정창 리소스, 갤러리
리소스, 앱 전역 리소스에 차례로 다시 썼다. 문구는 곧바로 바뀌었지만 WPF의
`DynamicResource` 무효화와 레이아웃 계산이 같은 변경에 세 번 연속 발생해 선택
직후 짧은 버벅임이 남았다.

번역 키만 담긴 하나의 `ResourceDictionary`를 앱 전역 병합 리소스에 두고, 언어를
바꿀 때 새 사전을 만들어 기존 사전과 한 번 교체한다. 설정창과 갤러리는 같은 앱
리소스를 참조하므로 두 창의 고정 문구는 선택 이벤트 안에서 함께 바뀐다. 현재
보이는 카드 우선 갱신, 렌더 프레임 반환과 화면 밖 카드 24개 단위 처리도 그대로
유지한다.

실제 115개 항목이 있는 보관함에서 `Auto → English → Auto`를 전환했다. UI 자동화
선택 호출은 각각 15.8ms와 8.7ms에 반환됐고, 반환 직후 설정 제목, 갤러리 문구와
보이는 LINE 사진 카드의 언어가 모두 일치했다. 접근성 트리 전체 조회 시간은 이
입력 응답 수치에 포함하지 않았다.

다중 선택 드래그는 가상화 컨테이너를 추가 생성하지 않는다. 고정 카드 배치의
콘텐츠 좌표와 최대 500개 항목 인덱스만 비교해 화면 밖 선택을 유지한다. 포인터가
위·아래 72px 가장자리에 있을 때만 24ms 간격으로 2~8px씩 자동 스크롤하며,
휠 입력 뒤 180ms 동안 자동 이동을 쉬어 사용자의 직접 스크롤 방향을 우선한다.

## 2026-07-21 트레이 메뉴 열기

트레이 아이콘을 우클릭할 때마다 빠른 설정 창의 XAML, 테마 리소스와 이벤트를
처음부터 만들던 경로를 확인했다. 메뉴를 닫을 때 창을 없애는 대신 숨기고, 다음
우클릭에서는 상태와 위치만 갱신해 같은 창을 다시 사용하도록 바꿨다. 메인 창이
뜬 뒤 유휴 시간에 메뉴를 미리 준비해 첫 우클릭에서 발생하는 생성 작업도 줄였다.

앱 종료 때는 재사용 창을 명시적으로 닫는다. 같은 메뉴 인스턴스를 계속 쓰고
생성 함수가 한 번만 호출되는지는 자동 테스트로 고정했다.

## 2026-07-25 자동 즐겨찾기 사용 세션

외부 메신저에서 같은 링크나 사진을 여러 번 사용했는지 판단하기 위해 원본 파일의
메타데이터를 다시 읽거나 보관함 전체를 순회하지 않는다. 기존 `capture_events`
기록을 바탕으로 항목별 `usage_sessions`만 관리하며, 6시간 이내에 이어진 저장은
같은 세션의 마지막 시각만 갱신한다.

새 저장이 적용될 때 수행하는 작업은 해당 항목의 마지막 세션 조회, 세션
삽입·갱신, 최근 30일 세션 수 집계뿐이다. 두 테이블 모두 항목 ID와 시간 표현식의
복합 인덱스를 사용하므로 다른 항목의 기록은 조회하지 않는다. 설정 기준에 도달한
경우 즐겨찾기 갱신도 같은 SQLite 트랜잭션 안에서 처리한다.

DB 스키마 6으로 처음 올라갈 때는 기존 캡처 이벤트를 시간순으로 묶어 세션을 한
번만 복원한다. 이후 앱 시작과 갤러리 새로 고침에서는 이 계산을 반복하지 않는다.

## 2026-07-27 사용 메타데이터 동기화

복사 횟수는 매번 전체 원격 이력을 더하지 않고 `정규화 키 + 기기 ID`별 절대
누적값의 최댓값만 SQLite에 유지한다. 따라서 같은 작업을 다시 받아도 횟수가
중복 증가하지 않으며, 여러 기기의 값은 합계 쿼리 한 번으로 계산한다. 항목을
삭제할 때 해당 키의 구성값도 함께 지워 새로 저장한 카드는 0회부터 시작한다.

같은 클라우드 저장소에서 설정의 기기 ID와 SQLite 저널의 기기 ID가 달라져
연결을 복구할 때는 `sync_item_copy_components`를 지우지 않는다. 합산 결과만
남기고 구성값을 지우면 그 합계를 새 기기의 로컬 사용량으로 다시 게시한 뒤
기존 원격 구성값까지 더해져 복구할 때마다 횟수가 증폭되기 때문이다. 사용자가
실제로 다른 저장소로 변경한 경우에만 구성값을 초기화해 현재 합계를 새 저장소의
기준값으로 다시 내보낸다.

외부 사용 세션은 자동 즐겨찾기에 필요한 최근 30일 구간만 작업 본문에 넣고
항목당 512개로 제한한다. 동기화 주기마다 직전 본문 지문을 비교해 실제 메타데이터가
달라진 항목만 새 작업을 만들며, 받은 작업을 적용한 직후 현재 지문을 기록해
반대편으로 같은 내용을 되돌려 보내지 않는다.

## 2026-07-28 WPF 이미지 최적화 롤백

보관함 사진 메모리를 낮추기 위해 카드 해상도 분리, 지연 디코딩, 화면 근처만
불러오는 스케줄러, 디스크 썸네일 캐시와 최근 항목 유지 정책을 차례로 시험했다.
메모리와 디코딩 CPU는 일부 낮아졌지만 마우스 휠 한 번의 체감 이동량, 빠른
스크롤바 드래그와 앱 전체 반응성이 최적화 이전보다 나빠졌다.

제품의 우선순위는 낮은 메모리 숫자보다 입력에 즉시 반응하는 갤러리다. 따라서
WPF 갤러리 코드는 메모리 최적화 직전 커밋 `d0d8a30`의 동작으로 복원한다.
실험에서 만든 지연 로더, 디스크 썸네일 캐시와 전용 테스트는 제품 코드에 남기지
않는다. 메모리 구조를 다시 변경하는 대신 WeChat 지원과 1.5.0 릴리즈를 먼저
완료한 뒤 갤러리 렌더링 계층을 WebView2로 교체한다.

WebView2 전환에서는 C#의 감지·SQLite·동기화 계층을 유지하고 갤러리만 앱 내부
웹 렌더러로 바꾼다. 빠른 휠과 스크롤바 드래그가 이미지 디코딩과 분리되는지,
현재 화면과 인접 영역만 로딩되는지, 사진이 폭포수처럼 자연스럽게 나타나는지를
완료 기준으로 삼는다. 상세 계획은 `docs/10-webview2-gallery-roadmap.md`에 있다.

## 2026-07-29 최소 디코딩 해상도 분리

롤백 이후 모든 사진·링크 미리보기·사이트 아이콘을 폭 480px로 디코딩하던 경로에서
표시 크기만 다시 분리했다. 갤러리 카드 사진과 링크 미리보기는 384px, 사이트
아이콘은 64px, 상세 사진과 상세 링크 미리보기는 480px로 읽고 각각 독립된 약한
LRU 캐시를 사용한다. 상세 사진 참조는 상세창을 열기 전까지 디코딩하지 않는다.

카드 이미지는 기존과 같이 목록 ViewModel을 만들 때 즉시 읽는다. 500ms 지연,
가시 범위 판정, 카드 이미지 해제, 디스크 썸네일 캐시와 최근 항목 유지 정책은
도입하지 않았다. 따라서 이번 변경은 휠·스크롤바 반응 경로를 건드리지 않으면서
작게 표시되는 이미지의 불필요한 디코딩 픽셀만 줄이는 제한된 최적화다.

## 2026-07-29 갤러리 시작·필터·정렬 부하 재조사

이전 측정은 UI 자동화 클릭 호출의 반환만 재고 실제 카드 렌더 완료를 포함하지
않아 체감 버벅임을 충분히 설명하지 못했다. 스크린샷 안정화까지 다시 재자
전체→사진 전환에 약 1초 이상 걸리는 경우와, 30초 클라우드 동기화가 겹치면
1.2초 이상까지 늘어나는 경우를 확인했다.

실제 보관함은 116개이고 사진 원본 77개의 합계가 428.9MB였다. 시작 때 모든
원본을 카드 폭으로 디코딩해 창 표시 뒤에도 약 9~10초 CPU·디스크 작업이
이어졌다. 원본 경로·크기·수정 시각을 키로 하는 384px JPEG 카드 캐시를
`%LOCALAPPDATA%\Sentory\cache\gallery-card-thumbnails\v3`에 두고, 최초 생성과
디코딩을 하나의 저우선순위 백그라운드 큐에서 직렬 처리한다. 기존의 스크롤
정지 대기나 500ms 지연은 되살리지 않아 새 카드가 보이면 즉시 로딩을 시작한다.

필터 결과 변경이 작으면 Remove·Insert·Move로 남는 카드 컨테이너를 재사용한다.
변경 알림 예상 수가 32개 이상이면 컬렉션을 한 번의 Reset으로 바꿔, WPF가
수십 번 연속 측정·배치하는 반대쪽 병목을 피한다. 범위 Add·Remove 알림은 실제
WPF `ItemsControl`에서 지원되지 않아 사용하지 않는다.

실제 v32에서 탭 클릭 핸들러는 약 58~59ms에 반환됐다. 이미 한 번 표시한 탭은
스크린샷 안정화까지 약 264~360ms였고 링크 전환은 약 394~440ms였다. 최초 사진
탭은 비트맵이 직렬로 채워져 측정 도구상 약 1.1초가 걸렸지만 탭 선택과 카드
배치는 먼저 끝나며 UI 스레드는 디코딩을 기다리지 않는다.

시작 후 즉시 클라우드 폴더를 순회하던 작업은 첫 갤러리 프레임과 감지 워커가
안정되도록 8초 뒤 시작한다. 언어 변경·필터·정렬·검색·탭 입력은 진행 중인 동기화 읽기를
`CancelAsync`로 UI 스레드를 막지 않고 중단하며, 2초간 추가 입력이 없으면 같은
원자적 동기화 절차를 자동 재시도한다.

Release 전체 테스트는 Core 60개, Diagnostics 15개, Platform Windows 425개,
Infrastructure 185개, App 184개로 총 869개가 통과했다.
