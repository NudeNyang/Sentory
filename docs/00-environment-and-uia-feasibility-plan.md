## 초기 UIA 접근성 관찰

민감한 화면 텍스트와 대화 내용은 출력하지 않고 컨트롤 유형, 클래스, 포커스 가능 여부만 조회했다.

- Discord 현재 주 창
  - UIA 하위 요소가 `Pane` 2개만 노출됨
  - 입력창, 버튼, 메시지 항목은 현재 조회에서 식별되지 않음
  - Electron/Chromium 접근성 트리가 현재 실행 상태에서 활성화되지 않았을 가능성이 있음
- KakaoTalk 현재 기본 창
  - UIA 하위 요소 25개가 모두 `Pane`으로 노출됨
  - `EmbeddedBrowserTabRootView` 포커스 가능 요소 1개가 보임
  - 현재 기본 창에서는 입력창, 전송 버튼, 메시지 항목이 식별되지 않음
  - 실제 개별 채팅창을 연 상태에서 별도 조사해야 함

이 결과는 최종 불가 판정이 아니다. 다만 표준 UIA만으로 필요한 신호가 충분히 나오지 않을 위험이 높으므로, 첫 구현 대상은 수집 앱이 아니라 진단 도구로 제한한다.

## 선행 준비

1. 공식 .NET 8 SDK x64 설치
2. 빈 솔루션과 `Sentory.Diagnostics` WPF/콘솔 진단 프로젝트 생성
3. UIA 이벤트 구독과 트리 스냅샷 기능 구현
4. 민감 정보 비기록 정책을 진단 도구에도 기본 적용

진단 도구는 이름과 값 원문을 기본적으로 저장하지 않는다. 컨트롤 유형, AutomationId, ClassName, 지원 패턴, 런타임 ID의 비가역 해시, 구조 변화, 시간 정보만 기록한다. 사용자가 명시적으로 허용한 테스트 문자열만 일시적으로 상관관계 확인에 사용한다.

## 앱별 검증 시나리오

테스트는 Discord의 전용 비공개 테스트 채널 또는 자기 자신과의 대화, KakaoTalk의 `나와의 채팅`처럼 외부 상대에게 영향을 주지 않는 공간에서 수행한다.

모든 테스트 콘텐츠는 고유 correlation token을 포함한 무해한 URL 또는 작은 테스트 파일로 만든다.

### Discord

| 항목 | 검증 방법 | 통과 기준 |
|---|---|---|
| 입력창 식별 | 포커스 이동과 UIA 이벤트 비교 | 채팅방 변경 후에도 안정적으로 재탐색 가능 |
| 입력 상태 | 붙여넣기, 삭제, 줄바꿈, IME 조합 비교 | 후보 생성/취소를 구분할 신호가 재현됨 |
| 첨부 미리보기 | 단일/복수 파일 드롭 후 구조 변화 비교 | 첨부별 최소 식별자 또는 개수 추적 가능 |
| 내 새 메시지 | 고유 테스트 URL 전송 전후 메시지 목록 비교 | 새 발신 항목과 기존/수신 항목 구분 가능 |
| 파일 정보 | 테스트 파일 첨부 전후 속성 조사 | 파일명 또는 후보 해시와 연결 가능한 안정 신호 존재 |
| 전송 실패 | 네트워크 차단 등 안전한 실패 테스트 | 실패/재시도 상태를 성공과 구분 가능 |

| 전송 실패 | 안전한 실패 조건에서 UI 변화 조사 | 실패 상태가 성공 판정 전에 검출됨 |

## 전송 확인 판정 기준

키보드나 마우스 이벤트는 commit 조건이 아니라 상관관계용 힌트로만 사용한다.

### Confirmed 최소 조건

다음 조건을 모두 만족해야 한다.

1. 같은 앱, 프로세스, 창, 대화방 해시의 `Pending` 후보가 존재함
2. 후보 이후 전송 시도 힌트 또는 전송 버튼 상태 변화가 존재함
3. 후보와 내용/첨부가 일치하는 새 발신 메시지 UI 노드가 생성됨
4. 입력창 또는 첨부 영역이 정상적인 전송 후 상태로 전환됨
5. 실패, 재시도, 취소 표시가 없음
6. correlation ID가 아직 commit되지 않음

신호가 부족하거나 서로 충돌하면 `Confirmed`로 전환하지 않는다.

### 즉시 fail-closed 처리

- 입력창이나 메시지 목록 선택자를 잃음
- 현재 사용자 발신 여부를 판별할 수 없음
- 새 메시지와 후보 콘텐츠의 대응 관계가 모호함
- 첨부 업로드 완료 여부를 판별할 수 없음
- 앱 업데이트로 트리 특징이 기준 스냅샷과 크게 달라짐
- UIA 호출이 반복적으로 타임아웃됨
- 대화방 전환 여부를 안정적으로 식별할 수 없음

이 경우 해당 앱 어댑터를 `DetectionUnavailable`로 바꾸고 저장을 중지한다.

## 드래그 앤 드롭의 별도 위험

다른 프로세스로 전달되는 OLE `IDataObject`를 제3의 백그라운드 앱이 공개 API만으로 항상 수동 관찰하는 기능은 보장되지 않는다.

따라서 1차 검증은 다음 순서로 한다.

1. UIA로 첨부 미리보기 생성과 소멸을 확인
2. Explorer에서 시작된 드래그의 원본 파일 목록을 안전하게 얻을 수 있는 공개 경로 조사
3. 얻을 수 없다면 최근 Shell 선택 항목이나 커서 위치를 근거로 추측하지 않음
4. 원본 파일을 정확히 연결하지 못한 경우 메타데이터만 기록하거나 해당 사례를 미지원 처리
5. 브라우저 이미지 드래그는 원본 URL/바이트가 명확히 확보되는 경우에만 지원

드롭 대상 앱의 정상 OLE 동작을 후킹하거나 가로채는 방식은 사용하지 않는다.

## 판정 게이트

### Gate A: 트리 가시성

입력창, 첨부 영역, 메시지 목록 중 핵심 요소가 UIA/접근성 API에 안정적으로 노출되어야 한다.

### Gate B: 발신 메시지 구분

새로 생성된 현재 사용자 발신 메시지를 기존 메시지 및 상대 메시지와 구분할 수 있어야 한다.

### Gate C: 콘텐츠 상관관계

Pending URL/이미지/파일과 새 발신 메시지를 잘못 연결하지 않고 일치시킬 수 있어야 한다.

### Gate D: 실패/취소 구분

전송 성공, 업로드 중, 실패, 취소를 구분할 수 있어야 한다.

### Gate E: 성능과 안정성

UIA 감시가 메시지 입력/전송을 가로막지 않고, 앱 멈춤이나 UIA 지연이 Sentory로 전파되지 않아야 한다.

앱별로 A~E를 모두 통과한 범위만 MVP 지원 대상으로 확정한다. 한 앱이 실패해도 다른 앱의 검증과 구현은 독립적으로 진행한다.

## 검증 후 구현 결정

- 전체 통과: 해당 앱의 URL/이미지/파일 전송 감지 어댑터 구현
- 일부 통과: 신뢰할 수 있는 콘텐츠 유형만 제한 지원
- 발신 구분 실패: 해당 앱 자동 저장 미지원
- 첨부 상관관계 실패: URL만 지원하고 이미지/파일 자동 저장 제외
- 접근성 트리 실패: 안전한 공개 API 대안이 없다면 해당 앱 지원 보류

DLL 주입, 프로세스 변조, 패킷 감청, TLS 가로채기, 메신저 파일 수정은 대안으로 사용하지 않는다.
