# Tauri UI 전환 로드맵

결정일: 2026-07-29

현재 상태: `codex/tauri-ui` 브랜치에서 전환 1단계를 진행한다. WPF 기준 화면의
정확한 치수와 색 토큰을 옮긴 시각 동등성 1차 작업과 작업표시줄 아이콘 수정까지
완료했다. 공개판 1.5.0과
기존 WPF 실행 경로는 유지하며, Tauri 개발자판이 기능·안정성·성능 기준을
충족하기 전에는 기본 실행 파일을 교체하지 않는다.

비교 기준은 별도 WebView2 갤러리 코드가 없는 WPF 1.5.0으로 고정한다. 새 Tauri
계열은 다음 세대 UI라는 의미로 2.0.0부터 시작하되, 데이터 형식과 C# 엔진 동작은
WPF 1.5.0을 기준으로 삼는다. 전환 중 생기는 차이는 UI 기반 변경으로 추적하며,
Tauri 2.0.0 표시는 아직 공개 배포를 뜻하지 않는다.

## 결정

Sentory의 사용자 인터페이스 기반을 WPF에서 Tauri 2로 단계적으로 전환한다.
갤러리만 별도 WebView2 컨트롤에 넣는 이전 시제품에서 범위를 넓혀, 검색·탭·필터·
정렬·선택·설정·상태 표시를 하나의 웹 UI 계층에서 렌더링한다.

메신저 감지, Windows UI Automation 작업자, 드래그·클립보드 추적, SQLite,
OCR, 링크 미리보기, 클라우드 동기화와 업데이트 정책은 검증된 C# 구현을 유지한다.
전체 백엔드를 Rust로 다시 작성하지 않는다. Tauri의 Rust 계층은 창 수명주기,
권한과 C# 엔진 연결을 담당하는 얇은 호스트로 제한한다.

## 목표 구조

```text
Tauri UI
  ├─ 갤러리 가상 스크롤과 지연 이미지 표시
  ├─ 검색·탭·필터·정렬
  ├─ 복사·즐겨찾기·삭제·선택
  ├─ 설정·다국어·테마
  └─ 상태·트레이·업데이트 화면
        │ 버전이 있는 로컬 IPC
        ▼
C# Sentory 엔진
  ├─ 메신저 감지와 UIA 작업자
  ├─ 캡처 판정과 저장
  ├─ SQLite와 파일 저장소
  ├─ OCR·링크 미리보기
  ├─ 클라우드 동기화
  └─ 업데이트·진단 정책
```

사용자에게는 하나의 Sentory로 배포한다. 내부 C# 엔진은 Tauri 사이드카로 함께
묶고, 임의의 웹 콘텐츠가 직접 실행하거나 파일 경로를 열 수 없도록 명령과 파일
범위를 제한한다.

## 전환 원칙

- 1.5.0 WPF판을 동작 기준선과 복귀 경로로 보존한다.
- Tauri와 C# 사이의 요청·응답에는 프로토콜 버전을 넣는다. UI와 엔진 버전이
  맞지 않으면 묵시적으로 동작하지 않고 이해할 수 있는 오류를 표시한다.
- 삭제, 파일 열기, 클립보드, 설정 변경처럼 상태를 바꾸는 명령은 C# 엔진에서
  항목 ID와 경로를 다시 검증한다.
- 웹 UI에는 원본 데이터베이스 접근 권한을 주지 않는다. 조회·변경은 모두 C#
  계약을 통한다.
- 갤러리는 전체 항목 수와 무관하게 보이는 행과 여유 행만 DOM에 둔다. 이미지는
  해당 카드가 생성된 뒤 읽고, 카드가 제거되면 브라우저가 참조를 회수할 수 있게
  한다.
- 초기 500개 스냅샷은 연결 검증용이다. 대규모 보관함 단계에서는 검색·필터·정렬을
  포함한 SQL 페이지 계약으로 바꿔 전체 DTO 보유량도 제한한다.
- WPF와 Tauri를 동시에 기본 UI로 유지하는 기간을 길게 끌지 않는다. 기능 동등성
  검수를 통과하면 WPF는 한 번의 안정화 기간 뒤 제거한다.

## WPF 시각 기준선

Tauri UI는 추정한 새 디자인이 아니라 실행 중인 WPF 1.5.0과
`GalleryWindow.xaml`을 함께 기준으로 삼는다. 기본 창은 WPF의 1180×780 논리 크기,
30/22/30/18px 헤더 여백, 360×42px 검색창, 13px 탭과 34px 도구 단추를 따른다.
갤러리는 252×320px 카드, 268×336px 가상 셀, 170px 이미지 행과 위아래 두 행
오버스캔을 사용한다. 카드 폭을 창에 맞춰 임의로 늘리지 않는다.

작업표시줄 아이콘은 한 자산을 두 용도로 읽지 않는다. Tauri 런타임 창 아이콘은
1024×1024 PNG를 사용한다. Windows 실행 파일 리소스는 `build.rs`에서 16·24·32·
48·64·128·256px 프레임이 든 ICO를 명시해 고해상도 작업표시줄과 파일 탐색기를
함께 지원한다. Tauri 2.6 코드 생성기가 ICO 첫 프레임만 RGBA로 푸는 동작 때문에
16px 아이콘이 확대되던 것이 기존 흐림의 원인이었다.

## 단계

### 0. 기반과 실제 데이터 연결

- C# 엔진 브리지 실행 파일과 프로토콜 1을 만든다.
- Tauri 셸이 사이드카를 실행하고 실제 Sentory 보관함을 읽는다.
- 검색·전체·사진·링크·즐겨찾기·메신저 필터와 최신·오래된순 정렬을 웹 UI에서
  즉시 적용한다.
- 가상 스크롤로 현재 화면과 위아래 두 행만 카드 DOM에 둔다.

### 1. 읽기·조작 기능 동등성

- 카드 상세, 링크 열기와 이미지 복사를 항목 ID 기반 C# 명령으로 이식한다.
- 즐겨찾기, 단일·다중 삭제, 선택 드래그와 가장자리 자동 스크롤을 이식한다.
- C# 엔진이 새 항목을 저장하면 UI에 증분 이벤트를 전달한다.
- 500개 제한을 SQL 페이지 조회로 바꾸고 빠른 스크롤 요청을 취소한다.

### 2. 앱 셸 기능 동등성

- 설정, 언어, 테마, 감지 상태와 Discord 복구 안내를 이식한다.
- 작업표시줄 복원, 트레이, 단일 인스턴스, 업데이트와 데이터 관리 화면을 이식한다.
- C# 엔진을 일회성 명령 실행이 아닌 장기 실행 프로세스로 바꾸고, 종료·재시작·
  프로토콜 불일치 복구를 검증한다.

### 3. 배포 전환

- x64·ARM64 설치형과 포터블 패키지에 Tauri UI와 C# 엔진을 함께 넣는다.
- WPF 기준판과 같은 데이터로 기능·메모리·시작·스크롤·감지 회귀를 비교한다.
- 기준을 통과한 뒤 Tauri를 기본 UI로 전환하고 WPF 전용 렌더러를 제거한다.

## 성능 판정 기준

- 118개·500개·2,000개 보관함에서 시작, 첫 카드, 탭·필터·정렬, 빠른 스크롤을
  각각 측정한다.
- Tauri, WebView2 자식 프로세스와 C# 엔진의 전용 메모리를 합산한다. 작업 관리자
  한 행만 비교하지 않는다.
- 2,000개로 늘려도 DOM 카드 수와 디코딩 이미지 수가 화면 크기에 비례해야 한다.
- 첫 선택 입력은 즉시 시각적으로 반영하고, 데이터 갱신은 다음 프레임에서 수행한다.
- 10분 빠른 왕복 스크롤 뒤 메모리가 계속 우상향하지 않고 안정 범위로 돌아와야 한다.
- Tauri UI가 중단되거나 재시작돼도 C# 감지와 저장이 끊기지 않아야 한다.

## 현재 구현의 의도적 제한

프로토콜 1은 구조 검증을 위해 C# 사이드카를 조회 때마다 실행하고 최근 500개를
한 번에 전달한다. 검색·필터·정렬과 DOM 가상화의 반응은 확인할 수 있지만, 최종
프로세스 구조와 대용량 DB 페이지 계약은 아니다. 삭제·복사·즐겨찾기 변경, 설정,
실시간 추가 이벤트도 다음 단계에서 붙인다.

기존 WPF WebView2 시제품 코드는 제거했으며 `docs/10-webview2-gallery-roadmap.md`만
종료된 실험 기록으로 보존한다. Tauri는 Windows에서 시스템 WebView2를 내부적으로
사용하지만, WPF 앱에 WebView2 컨트롤을 다시 넣지는 않는다. 시제품에서 확인한
프로세스 전체 메모리 측정법과 가상화 원칙만 이어받는다.
