# 클라우드 동기화 설계와 구현 순서

상태: 평문 v2와 항목 삭제·사용 메타데이터 자동 동기화 구현 완료

## 현재 구현 상태 (2026-07-27)

`codex/cloud-sync-domain`과 `codex/cloud-sync-item-projection`에서
운영체제와 클라우드 공급자에 의존하지 않는 전송·항목 반영 계층을 구현했다.

- 버전, 암호화 모드, 기기 ID, 작업 ID와 기기별 순번을 포함한 불변
  `SyncOperation`
- 작업 파일 직렬화, 크기 제한과 본문·파일 SHA-256 검증
- 목록·조건부 업로드·다운로드·존재 확인만 요구하는 `ISyncObjectStore`
- 로컬 작업, 게시 여부, 원격 적용 기록과 체크포인트를 보관하는 SQLite 저널
- 업로드 재시도, 오프라인 복구, 중복 수신 방지와 순번 누락·충돌을 감지하는
  `SyncCoordinator`
- 서로 격리된 두 SQLite 저장소와 메모리 가짜 클라우드로 검증하는 자동 테스트
- 버전 있는 URL·사진 메타데이터 작업 본문과 콘텐츠 해시 기반 사진 블롭
- 로컬 보관함 항목을 작업과 블롭으로 내보내는 `SyncItemExportService`
- 받은 작업을 기존 캡처 이벤트로 멱등 반영하는 `SyncItemProjectionService`
- 같은 URL·사진의 기존 카드 병합, 누락 블롭 재시도와 손상 블롭 차단
- 서로 격리된 A·B 보관함에서 링크와 사진이 정확히 한 번 나타나는 통합 테스트
- 클라우드 데스크톱 앱이 동기화하는 폴더를 사용하는
  `LocalFolderSyncObjectStore`
- 임시 파일·원자적 공개, 불변 키 충돌과 경로 이탈·심볼릭 링크 차단
- 복사 중인 부분 파일 제외, 객체 길이·SHA-256 검증과 안정된 목록 페이징
- 같은 실제 폴더를 공유하는 A·B 보관함의 링크·사진·재시작 통합 테스트
- 설정의 데이터 관리에서 공유 폴더 선택·변경과 동기화 켜기·끄기
- 설치별 영구 기기 ID와 SQLite의 항목별 원자적 내보내기 완료 기록
- 앱 시작, 새 캡처 신호와 30초 타이머에서 자동 송수신·보관함 반영
- 받은 항목의 재업로드 방지와 공유 폴더 변경 시 동기화 기록만 초기화
- 대기·동기화 중·완료·폴더 부재·손상·실패 상태 표시
- 사진·링크 삭제 tombstone과 오래된 추가·메타데이터의 재생성 차단
- 즐겨찾기의 최근 변경 우선 병합과 기기별 복사 횟수의 손실 없는 합산
- 최근 30일 외부 사용 세션, 자동 즐겨찾기 켜기·끄기와 2~5회 기준 동기화

현재 Windows 앱은 클라우드 데스크톱 앱이 동기화하는 로컬 폴더를 선택하면
단일 URL과 사진을 실제로 자동 동기화할 수 있다. 처음 켤 때 기존 항목도
200개씩 내보내며, 끄더라도 로컬 보관함과 공유 폴더의 객체는 지우지 않는다.
OneDrive·Google Drive API 직접 연동, 복원, 묶음과 링크
미리보기·OCR 메타데이터는 아직 이후 단계의 범위다. 단일 URL·사진 삭제는
tombstone으로 다른 컴퓨터에 전파하고 오래된 추가 작업의 재생성을 막는다.

사용자 검토 결과 개인·업무 보관함 분리와 Sentory 자체 종단간 암호화는
도입하지 않는다. 다음 형식은 사진을 표준 원본 파일, 링크를 읽을 수 있는
UTF-8 파일로 저장해 클라우드 웹·모바일에서 직접 보기·다운로드·공유할 수
있게 한다. 상세 규약과 비파괴적 이전은 `08-readable-cloud-storage.md`를
따른다.

## 목표

Sentory가 설치된 여러 컴퓨터에서 같은 사진·링크 보관함을 사용한다.
첫 지원 범위는 Windows 컴퓨터 사이의 동기화이며, macOS 앱이 정식으로
지원된 뒤 같은 프로토콜을 Windows와 macOS 사이에도 사용한다.

모바일 앱과 모바일 자동 감지는 현재 범위에서 제외한다. Slack 감지는
동기화 기반이 안정된 뒤 별도 기능으로 추가한다.

첫 공개 범위에서 사용자는 다음 동작을 기대할 수 있어야 한다.

- A 컴퓨터에서 저장한 사진·링크가 B 컴퓨터에 나타난다.
- 한 컴퓨터가 오프라인이어도 다음 연결 때 누락된 변경을 받는다.
- 즐겨찾기와 삭제 상태가 모든 연결 기기에 반영된다.
- 같은 사진이나 링크를 여러 기기에서 저장해도 중복 카드가 생기지 않는다.
- 원본 사진은 필요할 때 내려받고, 로컬 캐시는 별도로 비울 수 있다.
- 창 위치, 테마와 메신저 감지 설정은 기기마다 따로 유지한다.

## 확정한 제품 원칙

### 로컬 우선

각 기기는 자기 SQLite 데이터베이스와 사진 폴더를 사용한다. 네트워크가
없어도 현재 보관함을 열고 저장할 수 있으며, 연결이 돌아오면 대기 중인
변경을 전송한다.

`sentory.db`, SQLite WAL 파일이나 사용자 데이터 폴더 전체를 클라우드
드라이브로 직접 동기화하지 않는다. 파일 동기화 서비스는 SQLite 트랜잭션을
알지 못하므로 여러 기기의 동시 쓰기에서 변경 유실과 데이터베이스 손상이
발생할 수 있다.

### 공급자 중립

동기화 규약과 클라우드 공급자 구현을 분리한다. 동기화 엔진은 파일의 목록,
업로드, 다운로드와 존재 확인만 요구하고 OneDrive·Google Drive 같은
공급자별 인증과 API는 어댑터가 담당한다.

구현 우선순위는 다음과 같다.

1. 테스트용 메모리·파일 저장소
2. 사용자가 선택한 로컬 클라우드 동기화 폴더
3. OneDrive 앱 전용 폴더 직접 연동
4. Google Drive 앱 데이터 폴더 직접 연동
5. Dropbox 직접 연동
6. 수요를 확인한 뒤 MEGA SDK 직접 연동

MEGA는 직접 연동 전에도 MEGA Desktop이 동기화하는 로컬 폴더를 지정해
사용할 수 있다.

### 첫 버전은 Sentory 자체 종단간 암호화를 사용하지 않음

첫 버전은 사용자가 선택한 클라우드 공급자의 전송·저장 암호화와 계정
보안을 사용한다. Sentory는 최소 권한의 앱 전용 폴더만 요청하고 OAuth
토큰은 운영체제의 보호 저장소에 보관한다.

동기화 형식에는 `format_version`과 `encryption_mode`를 포함해 이후
개인용 비공개 보관함을 추가할 수 있게 한다. 첫 암호화 모드는 `none`이다.
체크섬은 전송 오류와 손상을 찾는 용도이며 악의적인 변조를
막는 전자서명으로 설명하지 않는다.

Slack 같은 업무 자료는 개인 클라우드로 자동 전송하지 않는다. Slack 지원
시에는 출처별 동기화 동의를 별도로 받고, 개인 보관함과 조직이 관리하는
업무 보관함을 분리하는 정책을 먼저 확정한다.

## 동기화 데이터 구조

클라우드에는 로컬 경로와 SQLite 파일 대신 불변 변경 묶음과 콘텐츠
블롭을 저장한다.

```text
Sentory Sync
├─ protocol.json
├─ devices
│  ├─ <device-a>
│  │  └─ operations
│  │     ├─ <sequence>-<operation-id>.json
│  │     └─ ...
│  └─ <device-b>
│     └─ operations
├─ blobs
│  └─ <content-id>.<extension>
└─ tombstones
   └─ <item-id>.json
```

- `device_id`: 설치마다 생성하는 안정된 ID
- `operation_id`: 재시도해도 한 번만 적용하기 위한 전역 고유 ID
- `sequence`: 같은 기기에서 발생한 변경의 단조 증가 순번
- `item_id`: 기기와 관계없이 같은 보관함 항목을 가리키는 ID
- `content_id`: 이미지 콘텐츠의 중복 식별자
- `format_version`: 읽기·쓰기 호환성을 판단하는 프로토콜 버전
- `encryption_mode`: 현재 `none`, 이후 암호화 형식 확장점

업로드가 끝난 변경 파일은 수정하지 않는다. 기기별 고유 경로와
`operation_id`를 사용해 클라우드 클라이언트의 이름 충돌을 피한다.
작은 변경이 지나치게 많아지면 동일 기기의 연속 변경을 불변 세그먼트로
묶되, 이미 공개된 세그먼트를 덮어쓰지 않는다.

## 동기화 대상과 기기별 설정

동기화 대상:

- 사진·링크와 묶음 구성
- 제목, 링크 미리보기와 OCR 결과
- 즐겨찾기
- 저장 시각, 출처, 기기별 복사 횟수와 최근 30일 외부 사용 세션
- 자동 즐겨찾기 사용 여부와 2~5회 기준
- 삭제와 복원 상태

기기마다 유지:

- 창 위치와 크기
- 테마와 화면 언어
- 필터와 정렬
- Discord·카카오톡·향후 Slack 감지 설정
- Windows 자동 실행
- 자동 정리 설정
- 내려받은 원본·썸네일 캐시

동기화 프로토콜의 출처 값은 오래된 앱이 모르는 값을 받아도 실패하지
않는 문자열 식별자로 전달한다. 현재 `SourceApp` enum을 네트워크
호환성 계약으로 그대로 사용하지 않는다.

## 삭제 정책

같은 보관함에서 `삭제`한 항목은 모든 기기에서 삭제하는 것이 기본이다.
삭제는 로컬 항목만 없애는 것으로 끝내지 않고 tombstone 변경으로 전파한다.
현재 평문 저장 방식에서는 모바일과 웹에서도 삭제 결과가 같도록 tombstone을
게시한 뒤 `Photos` 원본 또는 같은 URL의 `Links` 텍스트를 즉시 제거한다.
숨김 `.sentory`의 삭제 작업은 새 컴퓨터가 오래된 추가 작업을 되살리지 않도록
계속 보존한다.

1. A에서 삭제하면 A의 갤러리에서 즉시 숨긴다.
2. A가 tombstone을 업로드한다.
3. B가 다음 동기화에서 tombstone을 적용해 같은 항목을 숨긴다.
4. 삭제보다 오래된 즐겨찾기·복사·저장 변경은 무시한다.
5. 삭제 시각 뒤의 새 저장만 항목을 다시 만들 수 있다. 별도 복원 UI는 아직
   구현하지 않았다.

사용자 동작은 다음처럼 구분한다.

- `모든 기기에서 삭제`: 항목과 삭제 기록을 동기화
- `이 기기의 저장 공간만 비우기`: 현재 기기의 원본 캐시만 삭제
- 외부 원본 파일 삭제: Sentory가 관리하는 사본과 항목에는 영향 없음
- 클라우드 폴더 수동 삭제: 사용자 항목 삭제로 해석하지 않고 손상으로 처리

단일 사진은 콘텐츠 SHA-256 정규화 키로 하나의 동기화 항목으로 취급하므로
삭제 시 같은 키의 평문 사진 파일도 제거한다. tombstone 보존 기간과 복원
휴지통은 아직 구현하지 않았으며, 현재는 삭제 작업을 보존하고 새 저장의
시각이 삭제보다 최신일 때만 다시 만든다. 메인 기기와 수신 기기 양쪽 삭제,
반복 동기화 뒤 미재생성은 두 개의 격리된 SQLite 보관함으로 자동 검증한다.

## 충돌과 재시도 규칙

- 같은 `operation_id`는 여러 번 받아도 한 번만 적용한다.
- 같은 URL은 현재 URL 정규화 키로 합친다.
- 같은 이미지는 현재 콘텐츠 해시를 이용해 보관함 안에서 합친다.
- 삭제는 그보다 오래된 수정과 즐겨찾기보다 우선한다.
- 즐겨찾기는 가장 최근의 명시적 사용자 변경을 적용한다.
- 기기별 누적 횟수는 덮어쓰지 않고 기기별 값을 합산한다.
- 자동 즐겨찾기의 복사 기준과 사용 여부는 가장 최근 설정을 적용한다.
- 외부 사용은 기존과 같이 6시간 이내 전송을 한 세션으로 합치고 최근 30일
  세션만 자동 즐겨찾기 기준에 사용한다.
- 알 수 없는 필드와 출처 값은 보존하거나 무시하되 전체 동기화를 중단하지
  않는다.
- 알 수 없는 상위 `format_version`은 쓰기를 멈추고 업데이트 필요 상태를
  표시한다.
- 부분 업로드와 네트워크 오류는 같은 ID로 재시도한다.
- 유효하지 않은 크기·해시·스키마의 원격 데이터는 격리하고 나머지
  동기화는 계속한다.

## 한 컴퓨터에서 두 기기 검증

물리적인 컴퓨터가 한 대여도 A·B 기기를 시뮬레이션할 수 있게 한다.

자동 테스트에서는 서로 다른 임시 데이터 폴더의 두
`SqliteCaptureRepository`와 두 동기화 엔진을 같은 프로세스에 만든다.
가짜 저장소는 지연, 중복, 순서 변경, 부분 실패와 오프라인 상태를 주입할
수 있어야 한다.

개발자 UI 검수에는 다음 형태의 격리 실행을 제공한다.

```powershell
Sentory.exe --developer-device A --data-dir C:\Sentory-Test\A
Sentory.exe --developer-device B --data-dir C:\Sentory-Test\B
```

현재 앱의 `SENTORY_DATA_DIR` 지원을 재사용하되, 개발자 실행에서는
단일 인스턴스 mutex와 갤러리 열기 이벤트 이름을 데이터 폴더 또는
기기 ID별로 분리한다. 두 번째 인스턴스의 메신저 감지는 기본으로 꺼
중복 캡처를 막는다.

최종 실환경 검수는 본체와 Windows Sandbox·Hyper-V 같은 가상 컴퓨터를
같은 보관함에 연결해 수행한다.

필수 자동 시나리오:

1. A 추가 후 B에 한 번만 생성
2. 같은 변경의 중복 수신
3. B 오프라인 중 A 추가 후 재연결
4. B 오프라인 중 A 삭제 후 재연결
5. 오래된 B가 삭제 항목을 다시 업로드하지 않음
6. A·B 동시 즐겨찾기 변경
7. 사진 업로드 뒤 메타데이터 업로드 실패와 재시도
8. 동기화 중 종료 후 같은 지점에서 재개
9. 손상된 원격 변경을 격리하고 정상 변경은 계속 적용
10. 같은 사진을 참조하는 다른 카드가 있으면 블롭 유지

## 브랜치와 구현 단계

브랜치는 앞 단계의 검증과 커밋이 끝난 뒤 다음 단계로 진행한다.

### `codex/cloud-sync-foundation`

- 이 설계 문서와 결정 기록
- 데이터 손실·삭제·검증 기준 확정
- 구현 코드 변경 없음

### `codex/cloud-sync-domain`

- 운영체제 중립 동기화 모델과 저장소 계약 구현 완료
- 기기 ID, operation ID, 순번과 적용 체크포인트 구현 완료
- 메모리 가짜 클라우드 저장소 구현 완료
- 두 기기의 불투명 작업 전송·중복·오프라인·재시작·손상·충돌 테스트 완료

이 단계의 완료 기준은 A가 만든 작업 파일이 B의 동기화 저널에 정확히 한 번
저장되고, B가 오프라인이었다가 돌아와도 순서대로 따라잡는 것이다.

### `codex/cloud-sync-item-projection`

- URL과 사진 메타데이터 작업 본문 규약 구현 완료
- 이미지 콘텐츠 블롭 키와 크기·SHA-256 검증 구현 완료
- 받은 작업을 `SqliteCaptureRepository`의 보관함 항목으로 반영 완료
- 같은 URL·이미지 중복 병합과 사진 블롭 재사용 구현 완료
- A에서 추가한 링크와 사진이 B의 보관함에 정확히 한 번 나타나는 통합 테스트 완료

투영은 원격 `operation_id`를 캡처 이벤트 ID로 사용한다. 받은 작업 전체를
다시 확인하더라도 이미 적용한 이벤트는 횟수를 늘리지 않으므로, 사진 블롭이
늦게 도착하거나 앱이 중간에 종료된 경우 안전하게 재시도할 수 있다.

### `codex/cloud-sync-local-folder`

- 불변 객체 봉투 기반 로컬 폴더 어댑터 구현 완료
- 원자적 임시 파일 작성과 부분 복사·손상 검증 구현 완료
- 경로 이탈·심볼릭 링크·동일 키 충돌 차단 구현 완료
- 공유 폴더를 사용하는 A·B 링크·사진·재시작 통합 테스트 완료

사용자가 선택한 폴더 아래에는 다음 구조만 만든다.

```text
<선택한 클라우드 폴더>
└─ Sentory Sync
   └─ v1
      ├─ objects
      │  ├─ devices
      │  └─ blobs
      └─ temporary
```

각 `.sobj` 파일은 형식 버전, 본문 길이와 SHA-256을 가진 하나의 객체
봉투다. 로컬 쓰기는 `temporary`에 모두 기록하고 디스크에 반영한 뒤 같은
파일 시스템 안에서 최종 경로로 원자 이동한다. 다른 컴퓨터의 클라우드 앱이
최종 파일을 복사하는 동안에는 선언 길이와 실제 길이가 다르므로 목록에서
제외되고, 복사가 끝난 뒤에만 공개된다. 객체 하나의 첫 상한은 128MiB다.

### `codex/cloud-sync-app-wiring`

- 설정에서 로컬 클라우드 동기화 폴더 선택·변경과 켜기·끄기 구현 완료
- 설치별 기기 ID와 새 캡처의 원자적 내보내기 완료 기록 구현 완료
- 앱 시작·캡처·30초 주기 타이머에서 전송과 투영 자동 실행 완료
- 받은 원격 항목의 재업로드 방지와 공유 폴더 변경 시 안전한 재내보내기 완료
- 대기·동기화 중·완료·폴더 부재·손상·실패 상태 표시 완료
- 한 PC A·B 격리 자동 테스트 완료, 두 앱을 띄우는 개발자 실행 인자는 별도
  검수 도구 단계로 보류

### `codex/cloud-sync-delete-conflicts`

- 단일 URL·사진 tombstone과 삭제 우선 재생성 방지는 평문 저장 브랜치에서
  선행 구현 완료
- 즐겨찾기 최근 변경, 기기별 복사 횟수 합산, 외부 사용 세션과 자동
  즐겨찾기 설정 동기화 완료
- 30일 복원 UI, tombstone 만료와 이 기기 캐시만 제거
- 참조 없는 블롭 정리
- 묶음을 포함한 충돌 규칙 확장

### `codex/cloud-sync-onedrive`

- Microsoft 로그인과 앱 전용 폴더
- 최소 권한, 토큰 보호와 연결 해제
- 실제 네트워크 재시도와 할당량 오류

### `codex/cloud-sync-google-drive`

- Google 로그인과 앱 데이터 폴더
- 공급자 공통 회귀 테스트 재사용
- OneDrive와 동일한 사용자 동작 검증

### 동기화 안정화 이후

- macOS 앱이 준비되면 같은 프로토콜로 Windows↔macOS 검증
- Dropbox와 MEGA 직접 연동은 실제 수요를 확인한 뒤 추가
- Slack은 별도 브랜치에서 감지 가능성부터 조사하고 업무 보관함 정책을
  확정한 뒤 활성화
