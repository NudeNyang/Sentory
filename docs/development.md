# Sentory

## 목표

Sentory는 사용자가 메신저에서 다룬 URL, 이미지, 파일을 로컬에 보관하고 다시 찾을 수 있게 하는 데스크톱 앱이다.

현재 제품 런타임은 Windows 10/11 트레이 앱이다. 핵심 모델과 로컬
저장소는 운영체제 중립으로 유지하고, UI와 메신저 감지는 플랫폼별
프로젝트로 분리한다.

모든 데이터는 로컬에 저장한다. 메시지 본문, 상대 이름, 인증 토큰, 과거 대화 기록은 수집하지 않는다.

## Tauri 기본 앱

2026-07-30부터 Tauri 2 UI를 정식 기본 앱으로 사용한다. 메신저 감지, SQLite,
OCR, 링크 미리보기와 동기화는 기존 C# 엔진에 남기며 전체 Rust 재작성은 하지
않는다. 2026-07-31에 WPF 소스·테스트·배포 스크립트는 저장소에서 제거했으며,
마지막 1.5.1 개발자판만 `artifacts\developer-wpf-1.5.1`에 비상 백업으로 남겼다.

Tauri 앱을 빌드하려면 Node.js, Rust stable, Visual Studio C++ 빌드 도구와
Windows SDK가 필요하다. 저장소 루트에서 다음 스크립트를 실행하면 C# 브리지를 self-contained
단일 파일로 준비한 뒤 Tauri 실행 파일을 만든다. Rust 빌드는 메모리 압박으로 인한
간헐 실패를 피하도록 한 작업만 사용한다.

```powershell
.\scripts\Build-Tauri.ps1 -Configuration Release -Architecture x64
.\scripts\Build-Tauri.ps1 -Configuration Release -Architecture arm64
```

빌드 결과는 저장소 루트의 `Sentory.exe`와 `sentory-engine.exe`로 함께
배치된다. 현재 앱은
SQL 페이지 조회와 가상 스크롤, 상세·복사·삭제·즐겨찾기·다중 선택을 제공한다.
C# 사이드카는 시작 때 한 번 실행해 요청 사이에 재사용하며, 새 보관 항목 변화와
비정상 종료 뒤 자동 복구도 연결했다. 설정·언어·테마·감지 상태, 단일 인스턴스와
트레이, Windows 자동 실행, 데이터 관리와 GitHub Release 확인도 Tauri에
통합했다. 전환 순서와 성능 판정 기준은
[Tauri UI 전환 로드맵](./11-tauri-ui-migration-roadmap.md)을 따른다.

Tauri 앱의 제목 표시줄 닫기는 앱을 종료하지 않고 창을 알림 영역으로
숨긴다. 다시 실행하거나 트레이 아이콘을 더블클릭하면 기존 창이 복원된다. 테스트
뒤 앱과 C# 사이드카를 정상 종료하려면 트레이 메뉴의 `Sentory 종료`를 사용한다.
설정·상태·확인·알림 문구를 추가할 때는 네 언어를 함께 맞춘다. Tauri 정식
계열은 2.0.0부터 시작하며 기존 사용자 데이터 형식을 그대로 사용한다.

## 2026-07-16 확정된 앱별 동작

### Discord

- 실제 전송이 확인된 콘텐츠만 저장한다.
- 붙여넣기, 삭제, Shift+Enter만으로 저장하지 않는다.
- URL은 검증된 Ctrl+V 후보, 같은 Discord 입력창의 전송 키, 새 메시지의
  URL 일치를 조합해 확인한다.
- 사진은 검증된 입력창의 Ctrl+V 후보, 같은 Discord 입력창의 전송 키,
  새 메시지의 본인 이미지 첨부 표식을 조합해 확인한다.
- 파일, 드래그 앤 드롭, 전송 버튼, 실패·재시도는 추가 검증 대상이다.

### 2026-07-19 Discord 재연결 경고 조사

- 같은 Discord 프로세스에서 준비 성공 뒤 `message-list-unavailable`이
  발생하는 사례를 확인했다.
- 이 신호는 현재 화면에서 메시지 목록을 찾지 못했다는 뜻이며,
  접근성 모드가 꺼졌거나 Discord 재시작이 반드시 필요하다는 증거가 아니다.
- 수정 전 구현은 15회 연속 실패하면 `Discord 재연결 필요`로 승격해
  화면 이동이나 일시적인 접근성 트리 변화도 재연결 경고로 오인할 수 있다.
- 메시지 목록 부재와 창 전환 중 검증 실패는 `연결 준비 중`, 워커 장애는
  `워커 복구 중`으로 처리한다. 렌더러 접근성 루트 자체가 지속적으로
  없을 때만 `Discord 재연결 필요`로 분류한다.

### 2026-07-21 Discord 사진 간헐 누락 조사

- 1.1.0 설치판 로그에서 같은 Ctrl+V 사진 전송이 여러 차례 정상 저장된 뒤,
  사진 후보 생성과 Enter 감지까지 성공했지만 `message-list-unavailable` 한 번으로
  확인을 즉시 중단한 사례를 확인했다.
- 전송 직후 Discord 접근성 트리가 다시 구성되는 짧은 구간에는 입력창 검증이
  성공해도 메시지 목록이 한 번에 발견되지 않을 수 있다.
- 명시적인 Enter 전송을 이미 확인한 URL·사진·첨부 후보에 한해 메시지 목록이나
  렌더러 접근성 루트를 최대 세 번 다시 찾는다. 최종 저장에는 기존과 동일하게
  전송된 URL 일치 또는 본인 이미지 첨부 표식이 필요하다.
- 접근성 워커 예외 신호에는 원문이나 스택 전체 대신 예외 형식, 발생 메서드와
  HRESULT만 기록해 간헐적인 `ArgumentException`의 위치를 다음 재현에서 구분한다.

### 2026-07-21 첫 연결과 일반 파일 드래그 조사

- 새로 설치한 환경의 로그에서 Discord 메시지 목록이 준비되지 않은 동안
  사진과 URL 후보가 저장되지 않다가, 접근성 대상이 준비된 뒤 같은 전송이
  정상적으로 확인되는 흐름을 확인했다.
- 첫 연결 설정이 끝나지 않은 상태에서 Discord가 이미 실행 중이면 재시작
  안내를 표시한다. `연결 준비 중`과 `워커 복구 중`은 안내를 유지하고, 실제
  `감지 준비 완료` 상태에서만 준비 완료로 저장한다.
- `message-list-unavailable` 자체를 곧바로 재시작 필요 상태로 바꾸지는 않는다.
  채널 이동과 화면 전환에서도 같은 신호가 일시적으로 발생할 수 있기 때문이다.
- 탐색기에서 사진이 아닌 파일을 끌어 Discord나 카카오톡 위로 이동하면 감지
  영역을 즉시 닫고, 마우스 버튼을 놓을 때까지 같은 드래그를 다시 검사하지
  않는다. 일반 파일 전송은 원래 메신저가 그대로 처리한다.

### 단일 진단 로그

- 앱 로그와 Discord 접근성 작업자 로그는 데이터 폴더의
  `logs\sentory.log` 한 파일에 기록한다.
- 본 앱과 접근성 작업자가 동시에 기록할 수 있으므로 프로세스 간 잠금으로 한
  줄 단위 쓰기와 용량 정리를 보호한다.
- 로그가 1MB를 넘으면 별도 `previous` 파일을 만들지 않고 같은 파일 안에서
  오래된 줄을 정리한다.
- 기존 `logs\sentory.previous.log`와
  `diagnostics\discord-capture.log`는 첫 실행 때 시간순으로 통합하고 원본을
  제거한다.
- 문제 제보 때는 `%LOCALAPPDATA%\Sentory\logs\sentory.log` 하나만 받는다.

### 테마 선택

- 테마 선택 순서는 라이트 모드, 다크 모드, 시스템 테마다.
- 새 설정의 기본값은 라이트 모드이며 기존 사용자의 라이트·다크 선택을
  유지한다.
- 시스템 테마를 선택하면 Windows의 `AppsUseLightTheme` 값을 사용하고, 실행
  중 Windows 테마가 바뀌면 열려 있는 보관함과 설정창을 바로 갱신한다.
- 시스템 테마 선택 직후에는 현재 색상이 라이트인지 다크인지와 관계없이
  `시스템 테마 모드를 적용했습니다.`라고 안내한다.
- 개발자 검수판의 `for Developers` 표시는 설정의 버전 문구 오른쪽에 같은
  글자 크기와 색상으로 표시하며 별도 캡슐이나 강조 배경을 사용하지 않는다.

## Discord URL 캡처 필수 게이트

다음 조건을 모두 만족한 URL만 `Confirmed`로 저장한다.

1. 대상 프로세스가 `Discord.exe`
2. 전경 최상위 창과 Chromium 렌더러 HWND가 같은 Discord 프로세스에 속함
3. Ctrl+V 직후 클립보드에서 정규화된 URL 후보가 생성됨
4. 같은 Discord 입력창에서 Shift가 눌리지 않은 Enter 전송 키가 감지됨
5. 전송 뒤 입력값이 비었거나 전송 후 확인 모드로 전환됨
6. 붙여넣기 뒤 새로 식별된 `ListItem` 중 하나에 후보 URL이 존재함
7. 같은 후보 URL을 처리 중인 중복 워커가 없음

접근성 확인은 별도 장기 실행 Sentory 워커 프로세스에서 수행한다. 워커는
시작 시 메시지 목록을 준비하고, Discord 프로세스·창·렌더러·채널 제목이
같은 동안 검증된 접근성 대상을 재사용한다. 창이나 채널이 바뀌거나 캐시된
객체가 유효하지 않으면 캐시를 폐기하고 다시 찾는다. Discord 접근성 공급자가
멈추거나 구조가 달라지면 저장하지 않으며, 워커가 종료되면 다음 요청에서
새 격리 워커를 시작한다.
붙여넣기만 하거나 URL을 지우거나 Shift+Enter로 줄바꿈한 상태는 위 조건을
충족하지 않으므로 저장하지 않는다. Discord 화면 가상화에 대응하기 위해
항목 개수 대신 각 메시지의 안정된 접근성 지문을 비교한다. 후보는 최대
5분 후 만료된다.

같은 입력창에서 여러 URL을 따로 붙인 경우 Enter 시점에는 하나의 후보 묶음으로
확인하되, 접근성 작업자가 실제 전송 메시지에서 발견한 URL 목록을 응답에 함께
담는다. 런타임은 그 목록과 후보의 교집합만 저장하므로 입력창에서 삭제한 과거
URL은 제외되고, 실제로 함께 전송한 여러 URL은 모두 유지된다.

## Discord 사진 캡처 필수 게이트

다음 조건을 모두 만족한 클립보드 사진만 `Confirmed`로 저장한다.

1. 대상 프로세스와 Chromium 렌더러가 검증된 Discord 채팅창에 속함
2. Ctrl+V 시점의 클립보드 시퀀스가 사진 PNG 변환 전후로 유지됨
3. 같은 Discord 입력창에서 Shift가 눌리지 않은 Enter 전송 키가 감지됨
4. 붙여넣기 뒤 새로 식별된 `ListItem`이 화면에 표시된 상태임
5. 새 항목에 이미지 그래픽과 이미지·첨부 표식이 함께 존재함
6. 새 항목에 본인만 사용할 수 있는 `첨부 파일 수정` 표식이 존재함
7. 같은 SHA-256 사진 후보를 처리 중인 중복 워커가 없음

첨부 미리보기를 열기만 하거나 취소한 경우와 본인 이미지 첨부 표식을
확인하지 못한 경우에는 저장하지 않는다. Discord 화면 가상화와 연속 전송에
대응하기 위해 직접 항목 개수나 최신 메시지 하나만 사용하지 않고, 기준점
뒤의 새 메시지 집합을 확인한다. 관련 없는 메시지가 뒤이어 도착해도 후보를
즉시 폐기하지 않으며, 대응하는 이미지가 없으면 2분 뒤 폐기한다.

## Slack 캡처 필수 게이트

Slack 데스크톱 앱은 Discord와 마찬가지로 실제 전송이 확인된 콘텐츠만
`Confirmed`로 저장한다. 별도의 접근성 실행 옵션은 요구하지 않고 Electron이
공개하는 Windows UI Automation 트리를 사용한다.

1. 대상 프로세스가 `Slack.exe`이고 최상위 창 클래스가 `Chrome_WidgetWin_1`
2. 이벤트 대상 렌더러가 같은 Slack 프로세스의 `Chrome_RenderWidgetHostHWND`
3. 붙여넣기는 화면 아래쪽의 검증된 작성기 `Edit`에 포커스가 있을 때만 후보 생성
4. 탐색기 드롭은 실제 OLE `FileDrop` 경로에서 지원 이미지 파일만 읽음
5. 후보 생성 당시 대화 목록의 안정된 `message-list_*` ID를 기준점으로 보관
6. 같은 대화에서 기준점 뒤에 생긴 새 메시지가 현재 사용자 이름으로 시작
7. URL은 새 메시지의 표시 URL과 모두 일치하고, 사진은 파일명 또는 의미 있는
   이미지 접근성 요소가 확인됨

붙여넣기 직후 UI Automation 포커스 정보가 늦게 바뀌는 경우에는 75ms 간격으로
최대 세 번 더 확인한다. 매번 같은 작성기 `Edit` 조건을 통과해야 하며, 검색창 등
다른 Slack 입력란으로 판정되면 후보를 만들지 않는다.

붙여넣기나 드롭만 하고 보내지 않은 초안은 저장하지 않는다. 초안이 한 번
확인된 뒤 사라지면 실제 메시지가 나타날 시간을 10초 동안 기다리고, Enter
전송 키도 관찰되지 않았으면 후보를 취소한다. 마우스 전송 버튼은 전송 키가
없어도 같은 대화의 새 본인 메시지를 확인하면 지원한다. 후보는 최대 2분 뒤
만료되며, 접근성 구조·현재 사용자·대화가 불확실하면 fail-closed로 저장하지
않는다.

## WeChat 캡처 필수 게이트

WeChat은 `Weixin.exe`와 이전 이름인 `WeChat.exe`의 Qt 주 창만 대화 대상으로
허용한다. `WeChatAppEx.exe`는 업로드 중인 드롭 표면 확인에만 사용한다.

1. 붙여넣기 시점에 실제 WeChat 주 창과 `chat_input_field`,
   `chat_message_list`, 선택 대화를 확인해 후보 생성
2. 같은 WeChat 창이나 프로세스에서 Shift 없는 Enter 또는 검증된 전송 버튼
   입력을 후보 뒤에 한 번만 연결
3. 같은 대화의 기준점 뒤에 새 메시지 항목이 생긴 경우에만 전송으로 확정
4. 링크는 새 메시지 본문이 후보 URL을 모두 포함해야 하며, 사진은 새 사진
   메시지 항목이 확인돼야 함

Enter 키는 전역 저수준 훅에서 관찰하므로 그 콜백 안에서는 작성창 UI Automation
트리를 읽지 않는다. 훅은 네이티브 창·프로세스와 시각만 기록하고 바로 반환한다.
후보 등록보다 Enter가 먼저 끝난 빠른 전송은 같은 문맥의 최근 입력 시각을 한 번
재결합한다. 지운 URL 뒤 다른 문장을 보내거나 대화를 바꾸거나 메시지가 새로
생기지 않은 경우에는 저장하지 않는다.

### KakaoTalk

- 개별 채팅창의 검증된 메시지 입력창에 URL 또는 클립보드 이미지를 넣으면 즉시 저장한다.
- 실제 전송 여부는 확인하지 않는다.
- 갤러리에는 `입력 시 저장됨`으로 표시한다.
- 일반 텍스트는 저장하지 않는다.
- 클립보드 변경만으로 저장하지 않는다.
- 다른 앱, KakaoTalk 메인 검색창, 파일 선택 창, 백그라운드 KakaoTalk에는 반응하지 않는다.

KakaoTalk가 실제 발신 메시지를 공개 접근성 API에 노출하지 않아, 전송 확인형 저장은 지원하지 않는다.

## KakaoTalk 캡처 필수 게이트

다음 조건을 모두 만족해야 캡처 후보를 처리한다.

1. 대상 프로세스가 `KakaoTalk.exe`
2. 이벤트 당시 전경 최상위 창이 개별 채팅창
3. 포커스 HWND 클래스가 `RICHEDIT50W`
4. 입력 컨트롤 ID가 `1006`
5. 입력 HWND의 루트가 이벤트 당시 채팅창 HWND와 일치
6. 같은 채팅창에 메시지 목록 컨트롤이 존재
   - 클래스 `EVA_VH_ListControl_Dblclk`
   - 컨트롤 ID `100`
7. Ctrl+V 또는 이후 구현되는 검증된 입력/드롭 이벤트가 해당 입력창에서 발생

하나라도 불확실하면 저장하지 않는다.

## 사진 OCR 정책

- OCR은 `Sentory.Platform.Windows`에 포함한 PP-OCRv5 모바일 감지·분류·인식
  모델을 사용하며 원본 사진이나 인식 결과를 외부 서버로 보내지 않는다.
- 한국어용 인식기와 일본어·중국어·영어용 인식기를 함께 실행한 뒤 문자 구성,
  평균 신뢰도와 결과 길이를 비교해 더 적합한 후보를 고른다.
- 세로쓰기로 판단한 일본어 사진은 회전 후보도 검사해 읽는 순서를 보정한다.
- 이미지에서 차지하는 비율이 지나치게 작은 글자, 낮은 신뢰도의 조각과 장식
  문자는 검색용 본문과 자동 제목에서 제외한다.
- 파일명, 이미지 메타데이터와 OCR 제목 후보를 함께 평가한다. 의미 있는 원본
  제목은 유지하고 해시, 단순 일련번호와 일반적인 촬영 파일명은 OCR 결과보다
  정보가 적을 때만 대체한다. 다만 유효한 달력 날짜가 명확히 포함된 원본
  파일명은 숫자로만 되어 있거나 일반 촬영 접두사가 있어도 메타데이터·OCR보다
  우선한다. 잘못된 날짜와 단순 일련번호는 이 예외에 포함하지 않는다.
- 같은 SHA-256의 사진은 한 번만 처리하고, 묶음에 포함된 같은 사진도 인식 결과를
  공유한다. 백그라운드 작업은 한 번에 하나씩 실행하며 유휴 상태가 되면 모델
  메모리를 해제한다.
- OCR 대상은 원본의 생성 방식으로 구분하지 않는다. 직접 캡처한 파일, 탐색기에서
  가져온 이미지와 웹사이트 등에서 복사한 Windows 클립보드 비트맵이 지원
  메신저의 저장 조건을 통과하면 모두 같은 이미지 레코드와 OCR 대기열을 사용한다.
  단순히 클립보드에 복사했다는 이유만으로 읽거나 저장하지는 않는다.
- Tauri의 C# 엔진 호스트가 이미지·묶음 저장 직후 OCR 작업자를 깨우고, 동기화로
  새 이미지가 들어왔을 때도 다시 깨운다. 기존 미처리 사진은 엔진 시작 직후와
  유휴 상태의 15분 주기 확인에서 이어서 처리하며, 인식 결과가 바뀌면
  `gallery-changed` 이벤트로 화면과 검색 결과를 갱신한다.
- VirtualBox처럼 ONNX Runtime 네이티브 초기화가 불가능한 개발·검수 환경에서는
  사용자 환경 변수 `SENTORY_DISABLE_OCR=1`로 OCR 작업만 비활성화할 수 있다.
  일반 실행의 기본값은 계속 활성화이며 사진·링크 저장과 컴퓨터 간 동기화는
  이 변수와 관계없이 동작한다.
- 손글씨, 붓글씨, 매우 작은 글자와 복잡한 배치는 보조 대상이다. 낮은 품질의
  결과를 억지로 제목으로 만드는 대신 원본 파일명이나 기본 날짜 제목을 유지한다.
- 원본 사진의 `content_path`는 중복 제거와 무결성 확인을 위해 SHA-256 기반으로
  유지한다. 사진을 외부 앱으로 열 때만 보관함 제목으로 된 사본을 Windows 임시
  폴더에 만들며, 7일이 지난 사본은 앱 시작 시 정리한다.

## 링크 미리보기 정책

- URL은 먼저 로컬에 저장하고 미리보기는 별도 백그라운드 작업에서
  불러온다. 미리보기 실패가 메신저 감지나 URL 저장을 막지 않는다.
- 별도 사용자 옵션 없이 공개 웹 링크의 미리보기를 자동으로 불러온다.
- 페이지 본문은 보관하지 않고 제목, 짧은 설명, 사이트 아이콘과 대표
  이미지 캐시만 로컬 데이터 폴더에 저장한다.
- `http`와 `https`만 허용하며 로컬·사설 주소, 인증정보 포함 URL,
  과도한 리디렉션과 큰 응답을 차단한다.
- 기존 링크는 소량씩 순차 처리하고 실패한 링크는 30일 뒤 재시도한다.

## 데이터 관리 정책

- 모든 일괄 정리는 SQL 조건에서 즐겨찾기를 제외한다.
- 기간 정리는 최초 생성일이 아닌 `last_captured_at`, 즉 마지막 저장
  시점을 기준으로 한다.
- 즐겨찾기 제외 항목 전체 삭제는 대상 항목 수, 링크·사진 수, 사진
  용량을 보여주고 사용자 확인을 받는다.
- 자동 정리는 기본적으로 꺼져 있고 사용자가 7일, 30일, 90일, 180일 중
  하나를 선택한다. 일반적인 사용에는 90일을 권장한다.
- 자동 정리는 앱 시작 시와 실행 중 주기적으로 확인하되 하루에 한 번만
  수행한다.
- 백업 내보내기·가져오기는 현재 필수 기능에서 제외한다. 배포 범위와
  기기 이전 요구가 구체화될 때 별도 기능으로 검토한다.

## 크로스 플랫폼과 배포 기준

- `Sentory.Core`와 `Sentory.Infrastructure`는 `net8.0` 공통
  프로젝트로 유지한다.
- Windows 전용 Win32, 클립보드 및 카카오톡 감지는
  `Sentory.Platform.Windows`에만 둔다.
- Tauri 2만 Windows 제품 셸로 유지한다.
- 사용자 데이터는 설치 폴더 밖의 OS 표준 사용자 데이터 위치에
  저장한다.
- Windows 기본 경로 `%LOCALAPPDATA%\Sentory`는 기존 사용자와의
  호환을 위해 변경하지 않는다.
- Tauri 공개 배포는 x64·ARM64 self-contained 설치형과 포터블 패키지를 제공한다.
- 설정의 수동 확인은 GitHub에서 더 높은 정식 버전을 찾으면 공식 Release
  페이지를 연다. 패키지 교체는 사용자가 직접 진행한다.
- 설치 프로그램은 1.x와 같은 AppId와 설치 위치를 사용해 기존 사용자
  데이터와 자동 실행 설정을 이어받는다.
- Sentory의 원본 소스는 GNU GPL v3 전용(`GPL-3.0-only`)으로 공개한다.
  바이너리 또는 수정본을 배포할 때는 해당 소스와 라이선스 고지를 GPL 조건에
  맞게 함께 제공한다.
- 코드 서명은 인증서를 준비한 뒤 후속 배포에 적용한다. ARM64 패키지는 네이티브
  ARM64 Windows 러너에서 빌드와 자체 점검을 거치며, 실제 메신저 통합 검수는
  Windows on ARM 장치에서 별도로 진행한다.

세부 구조와 이식 순서는
[`03-cross-platform-and-distribution-readiness.md`](./03-cross-platform-and-distribution-readiness.md)에
기록한다.

## 개발 및 Git 작업 규칙

- 소스 코드, UI, 설정, 스크립트 또는 동작을 바꾼 모든 세션은 완료 전에
  `CHANGELOG.md`의 `개발 중` 항목과 로컬 인수인계 문서 `project.md`를 함께
  갱신한다. 성능·배포·감지 정책을 바꿨다면 해당 `docs/*.md`도 갱신한다.
- 변경 기록과 실제 `git diff`가 일치하는지 확인하기 전에는 작업 완료로
  보고하지 않는다.
- 파일 변경이 생긴 모든 작업은 변경 범위에 맞는 빌드와 테스트를 마친 뒤,
  관련 문서까지 포함해 의미 있는 작업 단위로 반드시 커밋한다.
- 커밋 메시지는 영어가 아닌 한국어로 작성한다.
- 원격 저장소 푸시와 Release 생성은 사용자가 명시적으로 요청한 경우에만 수행한다.
- 공개 문서의 제목과 부제목은 `이미지를 글자로 찾기`처럼 짧은 명사형으로
  작성한다. `~합니다`, `~했습니다`나 물음표로 끝나는 완전한 문장은 사용하지
  않는다.
- 자동 실행 설정은 새 설치에서만 기본으로 켠다. 기존 설정 파일에 선택값이
  없으면 현재 Windows 시작 프로그램 등록 상태를 가져오고, 이후 사용자가
  바꾼 값은 설정 파일과 레지스트리에 함께 기록한다. 설치 검증 프로세스와
  Discord 접근성 워커에서는 이 초기화를 실행하지 않는다.
- Windows 자동 실행과 Discord 감지를 모두 켠 경우에만 Discord 로그인 시작
  명령을 관리한다. 원래 값과 값 형식을 먼저 백업하고, 두 기능 중 하나를 끄거나
  앱을 제거하면 복원한다. 관리 중 사용자가 직접 바꾼 값은 덮어쓰지 않는다.
- Discord 사진 후보가 전송을 기다리는 동안에는 전송 전 첨부 제거 버튼 수를
  접근성 작업자에서 확인한다. 확인된 첨부 수가 줄었을 때만 500ms보다 오래된
  단일 사진 후보부터 취소하며, 첨부 버튼을 한 번도 확인하지 못한 환경에서는
  후보를 추측으로 삭제하지 않는다.
- 첨부 제거 버튼 조회는 메시지 목록 대상 검색과 분리하고 렌더러 HWND가 아니라
  메인 Discord 창의 현재 접근성 문서를 사용한다. 화면 하단의 채팅 초안 영역만
  100ms 간격으로 확인하고, 왼쪽 탐색 트리와 이름이 확인된 오른쪽 멤버 패널은
  순회하지 않는다. 현재 후보 수만큼 버튼을 찾으면 즉시 종료해 Enter보다 취소
  판정이 늦어지지 않게 유지한다.
- 인앱 업데이트 안내에는 `새 버전 {0}을 설치할 수 있습니다.`처럼 버전과
  설치 가능 여부를 담은 한 문장만 표시한다. GitHub Release 본문, 변경 기록,
  Markdown 원문은 안내창에 붙이지 않고 공개 Release 페이지에만 둔다.
- 커밋 전에는 변경 범위에 맞는 빌드와 테스트를 실행한다.
- UI를 추가하거나 수정할 때는 라이트 모드와 다크 모드의 배경, 글자,
  테두리, 선택 및 마우스 오버 상태를 모두 고려하고 두 테마를 함께
  확인한다.
- 보조 창, 확인창과 트레이 메뉴도 메인 창과 같은 공통 색상표와 모서리,
  간격 체계를 사용한다.
- 스크롤이 필요한 모든 화면은 WPF 기본 스크롤바 대신
  `OverlayScrollIndicatorController` 기반의 얇은 표시기를 사용한다. 스크롤
  중이거나 포인터가 가까울 때만 표시하고, 호버 확대와 왼쪽 버튼 드래그를
  동일하게 지원한다.
- 갤러리의 메신저 필터 목록은 `SourceApp` 항목을 기준으로 생성해 새
  메신저를 추가할 때 툴바나 팝업 구조를 다시 설계하지 않는다.

## 설치판 분리 진단

로컬 개발 데이터와 설치판 재현 데이터를 섞지 않으려면 실행 중인 Sentory를
모두 종료한 뒤 저장소 루트에서 다음 명령을 실행한다.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Start-InstalledDiagnostics.ps1 -Version 1.5.1
```

설치판의 데이터베이스, 설정, 캐시와 Discord 추적 로그는
`%LOCALAPPDATA%\Sentory-Diagnostics\1.5.1` 아래에 생성된다. 환경 변수는 실행한
프로세스와 그 접근성 작업자에만 전달되므로 기본 데이터 폴더와 시스템 환경
변수는 바뀌지 않는다. Windows 자동 실행이나 일반 바로가기로 연 Sentory는 이
진단 폴더를 사용하지 않으므로 재현할 때마다 위 스크립트로 실행한다.

## Discord 프로세스별 자동 연결 복구

1.4.2의 초기 준비 작업은 15회 실패 뒤 `worker-warmup-deferred
state=Connecting`을 남기고 끝났다. 이후 채팅방을 열어도 준비 작업이 다시
시작되지 않아 트레이와 설정이 계속 `연결 준비 중`으로 보일 수 있었다.

- Discord 메인 창 PID를 별도로 추적한다. 새 PID가 나타나면 진행 중인 준비
  대기를 즉시 깨우고, 준비 완료 상태였다면 새 접근성 대상을 다시 찾는다.
- 준비 완료 상태에서는 현재 메인 프로세스의 종료를 비동기로 기다린다. 평상시
  10초 확인 주기는 유지하지만 Discord가 먼저 종료되면 타이머 전에 깨어난다.
- 새 PID의 실제 명령줄은 WMI로 한 번만 읽는다. 접근성 옵션이 없으면 즉시
  15초 안내를 열고, 옵션이 이미 있거나 명령을 읽지 못했으면 재시작하지 않는다.
- Discord 감지를 꺼진 상태에서 켤 때는 자동 재시작 범위와 초안·통화 종료 가능성을
  먼저 설명한다. 사용자가 동의해야 설정을 켜며, 동의는 WebView 로컬 저장소의
  `sentory.discord-auto-restart-consent.v1`에 한 번 기록한다.
- 앱을 시작할 때 기존 설정에서 Discord 감지가 이미 켜져 있으면 그 선택을 동의로
  이전하고 다시 묻지 않는다. 이 이전은 대기 중인 자동 재시작 이벤트를 처리하기
  전에 끝낸다. 수동 `다시 연결`은 실행 직전의 별도 확인 절차를 그대로 사용한다.
- PID 변경 신호가 각 접근성 확인 뒤 2초 대기 중 들어오면 현재 묶음을 중단하고
  15회 초기 준비를 새로 시작한다. 신호를 소비하고도 이전 묶음의 남은 횟수를
  이어가거나 30초 저빈도 대기로 내려가면 안 된다.
- 초기 재시도 뒤에는 한 번에 한 차례만 접근성 대상을 확인하고 다음 확인까지
  30초 기다린다. 준비 완료 뒤 접근성 확인 작업은 종료되며 PID 조회만 10초
  간격으로 남는다.
- 메시지 목록 부재만 반복될 때는 로그인·채팅방 준비 중일 수 있으므로 재시작
  상태로 승격하지 않는다. 실행 옵션 누락이나 명시적인 접근성 루트 부재가
  확인됐을 때만 15초 카운트다운 창을 연다.
- 동일 PID에는 자동 안내를 반복하지 않는다. 창이 떠 있는 동안 Discord가
  자체 재실행되면 PID를 다시 비교해 오래된 프로세스에 대한 재시작을 건너뛴다.
- 재시작 실행을 결정한 시점에 `repairNeeded=false`, 상태 `Connecting`을 먼저
  UI에 적용한 뒤 Discord 종료를 기다린다. 실행 실패 시에는
  `repairNeeded=true`, `ReconnectRequired`를 복원한다.
- 메인 배너의 `나중에`는 재연결 필요 상태를 없애지 않고 배너만 접는다. 이때
  헤더의 작은 상태 표시는 `Discord 재연결 필요`를 유지해야 하며, 같은 실패
  상태가 다시 전달돼도 큰 배너를 자동으로 되열지 않는다.
- Discord 종료는 감시만 깨우며 앱을 자동으로 다시 실행하지 않는다. 사용자가
  새로 켠 Discord의 메인 창이 나타나면 다음 PID 판단을 시작한다.
- 재시작 직후에는 실제 접근성 캐시가 확인될 때까지 `Connecting`을 유지한다.
  준비 완료를 미리 표시하면 그 사이 전송을 놓쳐도 정상으로 보이므로 금지한다.

### Discord 미실행 상태 표시

- Discord 감지가 켜져 있어도 현재 메인 프로세스가 없으면 보관함의 수동 상태와
  재연결 배너, 트레이의 Discord 상태 행을 모두 숨긴다.
- 설정의 메신저 감지 카드는 이름 아래에 Discord의 실제 런타임 상태를 표시한다.
  재연결이 필요한 경우에는 Discord 행의 재연결 버튼도 함께 표시한다.
- 런타임의 `Connecting` 상태 자체는 바꾸지 않는다. 프로세스 존재 여부를 UI
  정책의 별도 입력으로 전달해 감지 준비 로직과 사용자 안내를 분리한다.

## 설정 메신저 1열 배치와 자동 화면 언어

- 설정의 메신저 감지는 화면 폭을 반으로 나누지 않고 Discord, KakaoTalk,
  Slack, WhatsApp, Telegram, LINE, WeChat 순서로 각 항목이 한 줄 전체를 사용한다.
  각 행은 메신저 이름, 한 줄 상태 문구와 작은 스위치를 표시한다. Discord
  재연결 버튼은 필요한 경우에만 나타난다.
- 저장 언어값 `auto`는 `CultureInfo.CurrentUICulture`의 두 글자 언어 코드를
  기준으로 `ko-KR`, `en-US`, `ja-JP`, `zh-CN`에 매핑한다. 지원하지 않는 시스템
  언어는 영어로 표시한다.
- 언어 선택 목록 첫 항목은 현재 표시 언어에 맞춰 `자동`, `Auto`, `自動`,
  `自动`으로 표시한다. 자동 모드에서도 실제 날짜·숫자 서식에는 해석된 구체적
  문화권을 사용한다.
- 언어 설정 버전이 없는 기존 `ko-KR` 값은 과거 기본값으로 보고 한 번만
  `auto`로 이전한다. 마이그레이션 뒤 사용자가 한국어를 직접 선택하면 설정
  버전이 유지되므로 다시 자동으로 바뀌지 않는다.

## 새 설치의 메신저 감지 선택

- 새 설정 파일은 일곱 메신저 감지를 모두 끄고
  `MessengerDetectionSetupCompleted=false`로 저장한다. Tauri는 첫 실행에서
  사용할 메신저를 고르는 창을 먼저 표시한다.
- 후보 표시는 현재 실행 중인 프로세스와 사용자·시스템 설치 경로만 확인한다.
  확인된 항목은 행 배경으로만 구분한다. 메신저 창이나 대화 내용은 읽지 않으며,
  후보로 표시해도 자동으로 켜지 않는다.
- Discord를 개별 선택하거나 `모두 켜기`로 포함할 때는 자동 재시작 동의를 먼저
  받는다. 거절하면 Discord는 선택하지 않는다. `선택 완료`는 모든 메신저 값과
  완료 여부를 하나의 설정 갱신으로 저장한다.
- 초기 선택창의 동의 상태는 앱 전체 WebView 동의 기록과 분리한다. 따라서 이전
  동의 키가 남은 개발·검수 환경에서도 선택창의 첫 Discord 선택에는 안내가
  나타나며, 같은 선택 세션 안에서는 한 번만 나타난다.
- 영구 동의 키는 동의 버튼을 누른 시점이 아니라 `settings_update` 응답에서
  Discord가 켜진 것을 확인한 뒤 기록한다. 신규 설정 화면에서는 오래된 키를
  먼저 지우며, Discord를 끈 채 선택 완료하면 설정 화면의 다음 ON에서 다시
  동의창을 표시한다.
- 완료 뒤 모든 감지를 끈 경우 메인 화면에 안내를 유지한다. 안내 버튼은 설정의
  메신저 감지 영역으로 이동하며, 하나라도 켜면 안내가 바로 사라진다.
- 완료 여부가 없는 기존 설정 파일은 이전 버전에서 사용하던 값으로 본다. 기존
  스위치 값은 유지하고 완료 처리해 첫 실행 선택창이 다시 나타나지 않게 한다.
  예전 파일에 새 메신저 항목이 없으면 당시 기본값이었던 켜짐으로 보완한다.

## 메신저 토글 비동기 저장

- 설정의 메신저 스위치는 변경값을 먼저 화면 상태에 반영하고, 엔진 저장은
  메신저별 비동기 큐에서 처리한다. 저장을 기다리는 동안 스위치나 설정창을
  잠그지 않는다.
- 저장 중 받은 전체 설정 스냅샷에는 변경 전 메신저 값이 들어 있을 수 있다.
  보류 중인 메신저 값은 `mergeSettingsSnapshot`에서 다시 덮어써 늦은 응답이
  현재 스위치를 되돌리지 못하게 한다.
- 같은 메신저를 연속으로 바꾼 경우 처리 중인 값과 마지막 선택값을 비교한다.
  값이 다르면 중간 응답은 화면에 적용하지 않고 마지막 값을 다음 요청으로
  저장한다. 마지막 요청이 실패한 경우에만 실제 저장값을 다시 불러온다.

## 안전 원칙

- 키 입력 전체를 기록하지 않는다.
- 필요한 조합만 관찰하고 훅 콜백은 즉시 반환한다.
- 메시지 입력과 전송을 가로채지 않는다.
- 클립보드는 검증된 Discord, Slack, WhatsApp, Telegram, KakaoTalk 또는 LINE 입력 이벤트
  직후에만 읽는다.
- URL과 이미지 이외의 일반 텍스트는 폐기한다.
- 입력값 원문은 로그에 기록하지 않는다.
- 앱 UI 구조가 달라지면 해당 어댑터를 `DetectionUnavailable`로 바꾼다.
- 데이터 중복보다 오탐 방지가 우선이다.

## 작업표시줄과 대화상자 복귀

Sentory의 확인창과 라이선스 화면은 Tauri 메인 WebView 안의 모달 레이어로
표시한다. 자동 Discord 재시작 안내가 필요하면 숨겨진 메인 창을 먼저 복원하고
포커스를 요청한다. 최초 동의가 저장된 경우에만 15초 카운트다운을 시작한다.

매우 빠르게 같은 작업표시줄 버튼을 반복 클릭하면 Windows 셸이 최소화와 복원을
번갈아 요청한다. 이때 애니메이션 도중의 반복 입력에서 시스템 경고음이 날 수 있지만,
창이 `Enabled=true`, `hung=false`를 유지하고 각 입력에 따라 최소화·복원이 이어지면
앱 활성화 실패가 아니다. 이 입력을 앱에서 가로채거나 최소화를 취소하지 않는다.
